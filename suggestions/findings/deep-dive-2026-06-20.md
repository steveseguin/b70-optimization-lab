# Deep Dive: B70 Qwen 35B Optimization Leads

Date: 2026-06-20

Scope: higher-effort source pass for Qwen3.6-35B-A3B / Qwen 35B on 4x
Intel Arc Pro B70, with emphasis on upstream XPU work, community B70
benchmarks, forks, driver/runtime versions, and XPU-specific project ideas.

## Executive Read

The highest-value additions from this pass are:

1. Upstream vLLM-XPU moved past the local kernel package. Local active
   `vllm-xpu-kernels` is `0.1.9.dev27+g28e1f5e`; upstream released
   `v0.1.10` on June 17/18 with GDN prefill, fused quant, FP8/MXFP8 GEMM
   consolidation, rotary, memory info, and PyTorch 2.12 work. Upstream vLLM
   PR #40367 merged the bump to `vllm-xpu-kernels v0.1.10` and UMD 26.18 on
   June 19.
2. The local driver/runtime stack is not the freshest known-good candidate.
   The machine is on Compute Runtime / OpenCL / Level Zero GPU packages
   `26.18.38308.1`; the configured PPA offers `26.18.38308.4`, and
   vLLM-XPU-kernels PR #424 is already staging a newer `26.22.38646.4` runtime
   profile with IGC `2.36.3`.
3. An exhaustive default-branch audit of the 76 public
   `vllm-project/vllm-xpu-kernels` forks found 6 identical heads, 60 stale or
   no-ahead forks, and 10 ahead forks. The highest-signal fork remains
   `jasonboukheir/vllm-xpu-kernels`, with one unique GDN cudagraph-padded
   metadata narrowing commit. Additional medium-value pattern leads include
   oneDNN W4A16 grouped GEMM, fused SiLU + block quant, MoE benchmark scripts,
   IPEX-derived RMSNorm/layernorm, and integer-width/index hardening.
4. LocalMaxxing and B70 community repos confirm the two big classes of wins:
   graph replay eliminates a massive host-launch wall on vLLM XPU, while
   hand-tuned llama.cpp SYCL work gets large gains from B70-specific decode
   kernels, dequant layout, graph cache, activation caching, and MoE
   gate/up handoff.
5. DFlash/DDTree/PFlash are now credible performance patterns, not just old
   experiments. Lucebox reports Qwen3.6-27B speculative speedups and
   LocalMaxxing has DFlash rows with acceptance-rate data. For B70/vLLM, the
   action item is still verifier/state correctness and XPU backend support,
   not simply enabling a flag.
6. A follow-on upstream `vllm` audit now maps the issue/PR surface to local
   code status. Highest-value additions: per-worker `ZE_AFFINITY_MASK`,
   torchcomms/XCCL communicator work, Qwen GDN projection fusion,
   `_chunk_cumsum_fwd_kernel` tensor-descriptor stores, DFlash mixed-KV
   plumbing, and XPU Triton test enablement. See
   `/home/steve/llm-optimizations/suggestions/findings/vllm-upstream-audit-2026-06-20.md`.

### LocalMaxxing: B70 llama.cpp SYCL kernel patterns

Source:
`https://localmaxxing.com/api/benchmarks?hardwareName=Intel%20Arc%20Pro%20B70&limit=80`

Rows for `nex-agi/Nex-N2-mini`, 1x B70, llama.cpp Q4_K_M:

- `106.52 tok/s`
- Notes: `dp4a fattn`, `V dequant 16B`, `NX2=2`, `BLOCK_SIZE=1`,
  scale-dequant predication, SYCL graph cache, `ACT_Q8_CACHE=1`,
  `GATE_UP_Q8_HANDOFF=1`.
- Notes claim the tuned path was `+59%` versus HEAD `67.09 tok/s`.

Transferable ideas:

- B70-specific dequant layout and vectorization can matter more than generic
  kernels.
- Graph cache/replay and activation caching are practical wins on B70.
- MoE gate/up handoff is a concrete pattern to compare against local W8A8
  layerlet/shared-expert work.

Not directly transferable:

- GGUF/K-quant llama.cpp kernels are not Quark W8A8 vLLM kernels.
- The value is in kernel-shape and dataflow ideas, not migrating this workload
  away from the current vLLM path.

### LocalMaxxing and Lucebox: DFlash/DDTree/MTP validation

Sources:

- `https://github.com/Luce-Org/lucebox-hub`
- `https://localmaxxing.com/api/benchmarks?hfId=z-lab%2FQwen3.6-27B-DFlash&limit=12`
- `https://localmaxxing.com/api/benchmarks?hfId=Qwen%2FQwen3.6-35B-A3B-FP8&limit=10`

Signals:

- Lucebox reports Qwen3.6-27B + PFlash around `5.6x` and Qwen3.6-27B +
  DDTree around `4.84x` relative to its vendored llama.cpp baseline.
- LocalMaxxing has a `z-lab/Qwen3.6-27B-DFlash` RTX 5090 Lucebox row at
  `215.43 tok/s`, acceptance length `8.83`, accept rate `55.2%`.
- LocalMaxxing has a Qwen3.6-35B-A3B FP8 Blackwell vLLM row at
  `253.7 tok/s` mentioning DFlash N=4 + CUDA graphs + greedy.
- LocalMaxxing has 27B MTP rows on RX 7900 XTX showing no-MTP
  `31.6 tok/s` versus MTP `50.24 tok/s`.

Inference: speculative decode is a real speed lever when verifier state and
graph execution are correct. For B70, the research should target DFlash/MTP
verifier correctness and XPU backend porting, not just drafter availability.

### LocalMaxxing: B70 multi-card llama.cpp negative/partial scaling

The `z-lab/Qwen3.6-27B-DFlash` B70 llama.cpp rows are useful because they
record concrete multi-GPU communication experiments:

- Single baseline noted as `24.723 tok/s`.
- 2x B70 with SYCL async `cpy_tensor`: `37.690081 tok/s`.
- 2x B70 with direct allreduce hook: `38.621476 tok/s`.
- 3x B70 direct peer allreduce: about `41.37-41.74 tok/s`.
- 4x B70 direct peer allreduce: `31.482389 tok/s`, explicitly submitted as
  negative scaling.

Inference: multi-GPU collectives/topology are fragile on B70. For vLLM TP4,
per-worker ZE visibility, oneCCL/torchcomms, and route/collective placement
are likely higher value than assuming all 4 cards should always help c1 decode.

`vllm-project/vllm-xpu-kernels`, fetched each public fork's default branch, and

- Behind or equal history, with no unique default-branch commits: 60

## New High-Value Implementation Options

These are research-to-implementation candidates, not changes made here.

### A. Rebase/bakeoff upstream vLLM-XPU kernels v0.1.10 plus selected PRs

Why: local package predates v0.1.10; upstream now has GDN, quant, GEMM,
rotary, memory, and PyTorch 2.12 changes. Selected open PRs (#392, #401,
#422, #429, #424) overlap the local bottlenecks.

How:

- Create a clean branch/environment; do not overwrite dirty local WIP.
- First test upstream v0.1.10 + local vLLM identity.
- Then cherry-pick one candidate at a time:
  - #392 reusable MoE workspaces
  - #401 MoE invalid-row activation skip
  - #422 fused qknorm/RoPE/KV-insert pattern if applicable
  - #429 stride-aware KV writes if model path uses packed/strided K/V cache
  - Jason GDN metadata narrowing commit if not superseded by upstream work
- Run canary before speed.

Risk: local dirty GDN WIP may conflict. This should be a parallel bakeoff, not
a replacement of the current branch.

### B. Controlled driver/runtime bakeoff

Why: local UMD is `26.18.38308.1`; PPA has `26.18.38308.4`; upstream PR #424
is moving to `26.22.38646.4` / IGC `2.36.3`.

How:

- Record current `sycl-ls`, `xpu-smi`, package versions, and launcher logs.
- Test the candidate runtime in an isolated image or restorable OS snapshot.
- Compare compile success, graph replay, canaries, and p512/n512 only after
  full identity capture.

Risk: driver movement can fix one thing and break graph capture or compilation.

### C. Per-worker `ZE_AFFINITY_MASK` / device visibility

Why: local launcher exposes all four devices globally. vLLM PR #46226 says
`xpu:<local_rank>` is not always enough isolation and proposes per-worker
masking so each TP worker sees one XPU. This can affect memory profiling,
KV sizing, and Level Zero/SYCL behavior.

How:

- Inspect PR #46226 and compare to local executor modifications.
- Test with TP4 under current graph identity.
- Validate worker logs: each rank sees exactly one XPU and uses worker-visible
  `xpu:0` internally.

Risk: could perturb distributed init and collective assumptions. Needs a clean
fallback path.

### D. XPU communicator path: torchcomms/XCCL

Why: vLLM PR #46210 is adding a torchcomms-backed XPU communicator. If it
reduces oneCCL friction or improves collective behavior, it could matter for
TP4 decode and future PP/EP layouts.

How:

- Track PR maturity; it is draft.
- Do not adopt until it has a minimal B70 TP test and fallback to current path.
- Compare collective-sensitive traces and not just endpoint tok/s.

Risk: early draft path may be correctness or stability work more than speed.

### E. B70 llama.cpp/SYCL pattern mining for vLLM W8A8

Why: community B70 work repeatedly finds gains in dequant layout, subgroup
size, graph cache, activation cache, and MoE gate/up handoff.

How:

- Mine only mechanisms that map to current vLLM shapes:
  - Quark W8A8 gate/up/down expert dataflow
  - shared-expert / layerlet handoff
