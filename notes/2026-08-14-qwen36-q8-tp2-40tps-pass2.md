## Static Q8 MMVQ code-generation audit

The accepted `mmvq.cpp` device bundle was extracted without loading the model
or running a GPU workload. `sycl-post-link --split=kernel` isolated each entry
point, `llvm-spirv` translated the selected modules, and `ocloc` generated
BMG-G31 assembly. Host-local evidence is under:

`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/igc-mmvq-accepted-smallgrf`

The active reordered Q8 decode kernel is the fourth lambda from
`reorder_mul_mat_vec_q8_0_q8_1_sycl` (`mmvq_67` in the split inventory). Its
static result is:

| Property | Accepted Q8 decode kernel |
| --- | ---: |
| Platform / SIMD | Xe2 / SIMD16 |
| GRF mode | 128 |
| IGC instruction count | 101 |
| register allocator | `LOCAL_ROUND_ROBIN_BC_RA` |
| scratch load/store traffic | none |
| weight load | one `load.ugm.d32x4.a64` |
| activation load | one `load.ugm.d32x4.a64` |
| scale loads | two `load.ugm.d16u32.a64` |

The upstream-compatible narrow control compiled to 121 instructions and seven
UGM loads. The phase arm compiled to 146 instructions. The deliberate mutant
compiled one operand as `d32x3`, which also positively identifies the active
wide/default entry point rather than relying on lambda suffixes alone.

This closes two tempting but invalid directions:

1. The kernel is already in BMG's 128-GRF high-occupancy mode. Forcing large
   GRF cannot increase residency.
2. There is no spill/fill or fragmented Q8 payload left to repair. Both 16-byte
   lane payloads are already single transactions, matching the previously
   measured ~591 GB/s isolated weight stream.

Four offline vISA register-allocation overrides (`-nolocalraroundrobin`,
`-noroundrobin`, `-nolocalra`, and `-forceGlobalRA`) were accepted by `ocloc`
but produced byte-identical assembly and the same allocator. They are not
runtime candidates.

## Next bounded candidate

Pass 1's local-memory collective-to-Q8 handoff showed a repeat-confirmed
`+0.958%` timing signal, but the first implementation placed a runtime branch
inside the accepted RMS/MUL kernel. Even its selector-off arm then produced a
different quality canary, proving that the experiment perturbed the compiler's
numerically sensitive kernel rather than isolating the treatment.

The next candidate will put the local handoff in separately named kernels and
leave the accepted global-store/barrier/reread lambdas textually unchanged.
The selector-off arm must first reproduce the promoted output hash. The
candidate must then match that hash (and the fixed 12-prompt suite) before any
speedup can be promoted.

## Isolated local collective-to-Q8 handoff: quality-exact, performance rejected

The follow-up was built in the separate
`/mnt/fast-ai/src/llama.cpp-q8-tp2-directq8-isolated` tree. It adds two
separately named, opt-in kernels behind `GGML_SYCL_COMM_DIRECT_Q8=1`; the
accepted selector-off lambdas remain textually unchanged. The new kernels
write the accepted FP32 RMS/multiply output to global memory and simultaneously
stage those exact values in 20 KiB of local memory before producing the Q8_1
handoff. This removes the subsequent global reread without changing the Q8
arithmetic.

Device-bundle isolation was checked before running the model. The candidate
contains exactly two additional entry points (79 kernels versus 77), while all
five existing `ggml_backend_sycl_comm_allreduce_add_rms_mul_tensor` kernels
have byte-identical SPIR-V after per-kernel splitting and translation. The two
new kernels compile for Xe2/SIMD16 with 128 GRFs, one barrier, no actual scratch
traffic, and 238/244 IGC instructions. Static artifacts are under:

`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/igc-collective-isolated-control`

The clean BMG-G31 AOT build completed under an 8 GiB cgroup ceiling and peaked
at 3.6 GiB without swap. Its final tool link was repeated under the pinned
oneAPI 2026.1 environment to supply the correct SYCL runtime-library path; no
GPU objects were rebuilt by that relink.

Both one-prompt endpoint canaries passed the fresh-response gate with zero
cached tokens and reproduced the promoted hash exactly:

`817e19c024fb382788008cc1609e5d88ae8db53b79fed08b1944586c61e6552b`

This is stronger isolation than the first quality-rejected implementation:

barrier. After the same ordered RMS reduction, each subgroup maps directly to
one 32-element Q8_1 block. Every FP32 result is computed once, stored to the
graph-visible MUL output, and retained in registers for the Q8 reduction and
packing. `GGML_SYCL_COMM_DIRECT_Q8=2` selects this arm; mode 0 remains the
unchanged accepted path and mode 1 preserves the rejected local-memory arm.

`817e19c0...` hash exactly with fresh responses and zero cached tokens. The
mode-2 canary measured 35.627263 tok/s versus 35.458414 for its immediately

## Dual-root collective: rejected by quality gate

A higher-concurrency prototype let each B70 independently compute the ordered
`(partial0 + partial1) + residual` result, allowing the two RMS/MUL/Q8 kernels
to start in parallel instead of making device 1 wait for device 0's root. The
first version lacked a cross-queue lifetime join and produced hash
`c6df0e42...`, so it was invalid regardless of speed. An explicit join was
then added after both device kernels to prevent the device-0 partial buffer
from being recycled while device 1 still read it.

The joined version passed the fresh-response mechanics (`cached_tokens=0`,
512 streamed tokens, final gate passed) but produced hash `eafafbec...`, not
the promoted `817e19c0...` oracle. Its one-prompt historical throughput was
35.108479 tok/s and is **not** a valid performance result. Recomputing the
root on device 1 is therefore not arithmetic-equivalent enough for exact
greedy generation on this path. The prototype was removed and is not stacked.
Both failed canaries are retained as `directq8-dual-root-canary.json` and
`directq8-dual-root-joined-canary.json` in the pass-2 artifact directory.

## IMRoPE-to-KV-cache direct write: quality-cleared, retained for stacking

A count-only fallback census was added to the isolated experimental tree. It
does not synchronize or profile the GPUs. Comparing `p0/n1` and `p0/n16`
showed the steady per-token fallback mix to be 258 MUL_MAT, 2 GET_ROWS,
64 SET_ROWS, 64 ROPE, 32 FLASH_ATTN_EXT, and 96 UNARY operations. The 384
SCALE operations are model-load/setup work rather than steady decode. This
identified the full-attention K-cache chain as a bounded launch-fusion target.

The existing SYCL direct RoPE-to-indexed-SET_ROWS path handled normal and NeoX
RoPE but not the MRoPE kernel used by Qwen3.5-family models. The experimental
implementation generalizes the MRoPE kernel's destination type, adds indexed
F16 cache writes, and accepts exact MROPE/IMROPE modes while continuing to
exclude vision RoPE. Qwen3.6 27B reports IMROPE (mode 40). With
`GGML_SYCL_FUSED_ROPE_SET_ROWS=1`, the `p0/n16` census recorded 544 fused
writes over 17 graph passes and reduced both fallback ROPE and SET_ROWS from
1088 to 544. That is exactly 32 eliminated RoPE launches and 32 eliminated
SET_ROWS launches per generated token.

The one-prompt cold quality canary passed with zero cached tokens, 512 streamed
tokens, and the exact promoted output hash
`817e19c024fb382788008cc1609e5d88ae8db53b79fed08b1944586c61e6552b`.
Its historical first-100 throughput was 35.922661 tok/s, retained only as a
quality canary rather than a performance claim.

## Allocation-free virtual-n5 MMVQ: rejected

The route audit found that the reordered-Q8 kernel measured `178.9 us` for
five real columns versus `192.6 us` for one real column at a dominant shape.
An earlier external one-to-five padding experiment lost `1.92%` end to end
because it added two pool allocations and three queue operations. A clean,
default-off prototype therefore invoked the existing five-column kernel for a
one-column tensor with zero activation and destination column strides. This
removed all external allocations, copies, and extra queue submissions while
retaining the same weight load across five accumulator chains.

The isolated oneAPI 2026.1 BMG-G31 AOT build completed under an 8 GiB hard
memory limit. The smallest candidate and same-binary control smokes were safe,
both cards remained normal, and no driver fault or reset occurred. A balanced
TP2 `p64/n256/r3` A-B-B-A screen then measured:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | control | 35.741443 |
| 2 | virtual n5 | 35.024330 |
| 3 | virtual n5 | 34.995657 |
| 4 | control | 36.770768 |

The control mean was `36.256106 tok/s`; virtual n5 averaged
`35.009994 tok/s`, a `-3.437%` regression. The five-column kernel amortizes a
weight load when it computes five distinct output columns, but zero strides do
not eliminate the five repeated dot products. The candidate was rejected
before endpoint quality testing and is not part of the promoted source or
runtime recipe.

This screen also exposed a reproducibility trap in llama.cpp's CLI syntax.
For `llama-bench`, `-dev SYCL0/SYCL1` selects one TP2 device group, while
`-dev SYCL0,SYCL1` emits separate SYCL0 and SYCL1 one-card tests. The server
uses the different `--device SYCL0,SYCL1` syntax. The promoted endpoint record
was already correct and is unaffected; the reproduction README now states the
front-end-specific separators explicitly.
