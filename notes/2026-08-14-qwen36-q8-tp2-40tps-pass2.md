## Static Q8 MMVQ code-generation audit

The accepted `mmvq.cpp` device bundle was extracted without loading the model
or running a GPU workload. `sycl-post-link --split=kernel` isolated each entry
point, `llvm-spirv` translated the selected modules, and `ocloc` generated
BMG-G31 assembly. Host-local evidence is under:

`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/igc-mmvq-accepted-smallgrf`

The active reordered Q8 decode kernel is the fourth lambda from
`reorder_mul_mat_vec_q8_0_q8_1_sycl` (`mmvq_67` in the split inventory). Its
static result is:

| Property | Accepted Q8 decode kernel |
| --- | ---: |
| Platform / SIMD | Xe2 / SIMD16 |
| GRF mode | 128 |
| IGC instruction count | 101 |
| register allocator | `LOCAL_ROUND_ROBIN_BC_RA` |
| scratch load/store traffic | none |
| weight load | one `load.ugm.d32x4.a64` |
| activation load | one `load.ugm.d32x4.a64` |
| scale loads | two `load.ugm.d16u32.a64` |

The upstream-compatible narrow control compiled to 121 instructions and seven
UGM loads. The phase arm compiled to 146 instructions. The deliberate mutant
compiled one operand as `d32x3`, which also positively identifies the active
wide/default entry point rather than relying on lambda suffixes alone.

This closes two tempting but invalid directions:

1. The kernel is already in BMG's 128-GRF high-occupancy mode. Forcing large
   GRF cannot increase residency.
2. There is no spill/fill or fragmented Q8 payload left to repair. Both 16-byte
   lane payloads are already single transactions, matching the previously
   measured ~591 GB/s isolated weight stream.

Four offline vISA register-allocation overrides (`-nolocalraroundrobin`,
`-noroundrobin`, `-nolocalra`, and `-forceGlobalRA`) were accepted by `ocloc`
but produced byte-identical assembly and the same allocator. They are not
runtime candidates.

## Next bounded candidate

Pass 1's local-memory collective-to-Q8 handoff showed a repeat-confirmed
`+0.958%` timing signal, but the first implementation placed a runtime branch
inside the accepted RMS/MUL kernel. Even its selector-off arm then produced a
different quality canary, proving that the experiment perturbed the compiler's
numerically sensitive kernel rather than isolating the treatment.

The next candidate will put the local handoff in separately named kernels and
leave the accepted global-store/barrier/reread lambdas textually unchanged.
The selector-off arm must first reproduce the promoted output hash. The
candidate must then match that hash (and the fixed 12-prompt suite) before any
speedup can be promoted.

## Isolated local collective-to-Q8 handoff: quality-exact, performance rejected

The follow-up was built in the separate
`/mnt/fast-ai/src/llama.cpp-q8-tp2-directq8-isolated` tree. It adds two
separately named, opt-in kernels behind `GGML_SYCL_COMM_DIRECT_Q8=1`; the
accepted selector-off lambdas remain textually unchanged. The new kernels
write the accepted FP32 RMS/multiply output to global memory and simultaneously
stage those exact values in 20 KiB of local memory before producing the Q8_1
handoff. This removes the subsequent global reread without changing the Q8
arithmetic.

Device-bundle isolation was checked before running the model. The candidate
contains exactly two additional entry points (79 kernels versus 77), while all
five existing `ggml_backend_sycl_comm_allreduce_add_rms_mul_tensor` kernels
have byte-identical SPIR-V after per-kernel splitting and translation. The two
new kernels compile for Xe2/SIMD16 with 128 GRFs, one barrier, no actual scratch
traffic, and 238/244 IGC instructions. Static artifacts are under:

`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/igc-collective-isolated-control`

at 3.6 GiB without swap. Its final tool link was repeated under the pinned

graph-visible MUL output, and retained in registers for the Q8 reduction and
packing. `GGML_SYCL_COMM_DIRECT_Q8=2` selects this arm; mode 0 remains the
unchanged accepted path and mode 1 preserves the rejected local-memory arm.

## Dual-root collective: rejected by quality gate

A higher-concurrency prototype let each B70 independently compute the ordered
`(partial0 + partial1) + residual` result, allowing the two RMS/MUL/Q8 kernels
to start in parallel instead of making device 1 wait for device 0's root. The
first version lacked a cross-queue lifetime join and produced hash
`c6df0e42...`, so it was invalid regardless of speed. An explicit join was
then added after both device kernels to prevent the device-0 partial buffer
from being recycled while device 1 still read it.

The joined version passed the fresh-response mechanics (`cached_tokens=0`,
512 streamed tokens, final gate passed) but produced hash `eafafbec...`, not
the promoted `817e19c0...` oracle. Its one-prompt historical throughput was
35.108479 tok/s and is **not** a valid performance result. Recomputing the
root on device 1 is therefore not arithmetic-equivalent enough for exact
greedy generation on this path. The prototype was removed and is not stacked.
Both failed canaries are retained as `directq8-dual-root-canary.json` and
`directq8-dual-root-joined-canary.json` in the pass-2 artifact directory.

## IMRoPE-to-KV-cache direct write: quality-cleared, retained for stacking

A count-only fallback census was added to the isolated experimental tree. It
does not synchronize or profile the GPUs. Comparing `p0/n1` and `p0/n16`
showed the steady per-token fallback mix to be 258 MUL_MAT, 2 GET_ROWS,
64 SET_ROWS, 64 ROPE, 32 FLASH_ATTN_EXT, and 96 UNARY operations. The 384
SCALE operations are model-load/setup work rather than steady decode. This
identified the full-attention K-cache chain as a bounded launch-fusion target.

The existing SYCL direct RoPE-to-indexed-SET_ROWS path handled normal and NeoX
RoPE but not the MRoPE kernel used by Qwen3.5-family models. The experimental
implementation generalizes the MRoPE kernel's destination type, adds indexed
F16 cache writes, and accepts exact MROPE/IMROPE modes while continuing to
exclude vision RoPE. Qwen3.6 27B reports IMROPE (mode 40). With
`GGML_SYCL_FUSED_ROPE_SET_ROWS=1`, the `p0/n16` census recorded 544 fused
writes over 17 graph passes and reduced both fallback ROPE and SET_ROWS from
1088 to 544. That is exactly 32 eliminated RoPE launches and 32 eliminated
SET_ROWS launches per generated token.

The one-prompt cold quality canary passed with zero cached tokens, 512 streamed

## Allocation-free virtual-n5 MMVQ: rejected

The route audit found that the reordered-Q8 kernel measured `178.9 us` for
five real columns versus `192.6 us` for one real column at a dominant shape.
An earlier external one-to-five padding experiment lost `1.92%` end to end
because it added two pool allocations and three queue operations. A clean,
default-off prototype therefore invoked the existing five-column kernel for a
one-column tensor with zero activation and destination column strides. This
removed all external allocations, copies, and extra queue submissions while
retaining the same weight load across five accumulator chains.

The isolated oneAPI 2026.1 BMG-G31 AOT build completed under an 8 GiB hard
memory limit. The smallest candidate and same-binary control smokes were safe,
both cards remained normal, and no driver fault or reset occurred. A balanced
TP2 `p64/n256/r3` A-B-B-A screen then measured:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | control | 35.741443 |
| 2 | virtual n5 | 35.024330 |
| 3 | virtual n5 | 34.995657 |
| 4 | control | 36.770768 |

The control mean was `36.256106 tok/s`; virtual n5 averaged
`35.009994 tok/s`, a `-3.437%` regression. The five-column kernel amortizes a
weight load when it computes five distinct output columns, but zero strides do
not eliminate the five repeated dot products. The candidate was rejected
before endpoint quality testing and is not part of the promoted source or
runtime recipe.

This screen also exposed a reproducibility trap in llama.cpp's CLI syntax.
For `llama-bench`, `-dev SYCL0/SYCL1` selects one TP2 device group, while
`-dev SYCL0,SYCL1` emits separate SYCL0 and SYCL1 one-card tests. The server
uses the different `--device SYCL0,SYCL1` syntax. The promoted endpoint record
was already correct and is unaffected; the reproduction README now states the
front-end-specific separators explicitly.

`576e2b218db70de5496fab2c8a611d9a96c3784cbcdfc180c2617d14a1221d12`.
Vec4 is therefore promoted as the new target-only record.

## Wider TP root vectors: rejected

After promoting vec4, a same-binary experiment tested otherwise identical
eight- and sixteen-float root reductions. The balanced `p64/n256/r3` order was
vec4, vec8, vec16, vec16, vec8, vec4:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | vec4 | 36.279033 |
| 2 | vec8 | 34.338186 |
| 3 | vec16 | 34.266300 |
| 4 | vec16 | 34.076271 |
| 5 | vec8 | 35.208356 |
| 6 | vec4 | 35.855138 |

Vec4 averaged `36.067086 tok/s`, vec8 averaged `34.773271 tok/s`
(`-3.587%`), and vec16 averaged `34.171286 tok/s` (`-5.256%`). The wider
loads reduce the number of independent root work-items too far for this small
5,120-element collective. Both candidates were rejected before endpoint
quality testing and are not included in the promoted patch or recipe.

## Two-float TP root vector: rejected as neutral

The missing point between the scalar and promoted vec4 implementations was
tested with the same ordered FP32 additions and a default-off
`GGML_SYCL_COMM_REDUCE_VEC2` selector. A `p64/n256/r3` A-B-B-A screen measured:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | vec4 control | 35.998832 |
| 2 | vec2 | 36.047193 |
| 3 | vec2 | 36.455796 |
| 4 | vec4 control | 36.540821 |

Vec4 averaged `36.269827 tok/s`; vec2 averaged `36.251495 tok/s`, or
`-0.051%`. The two implementations are indistinguishable at end-to-end scale,
so vec2 was rejected without an endpoint suite. The protected source was
restored to the published vec4 patch after the screen.

## Physical device/root ordering: rejected

The contributor-derived recipe had always enumerated the cards as
`ONEAPI_DEVICE_SELECTOR=level_zero:1,0`; logical rank 0 owns the fused TP root.
An eight-run, position-balanced `p64/n512/r3` test compared that order with
`level_zero:0,1` while holding logical devices and the equal tensor split
fixed:

| Sequence position | Selector | Decode tok/s |
| ---: | --- | ---: |
| 1 | `1,0` | 36.097156 |
| 2 | `0,1` | 37.010366 |
| 3 | `0,1` | 36.083473 |
| 4 | `1,0` | 36.278456 |
| 5 | `0,1` | 36.034784 |
| 6 | `1,0` | 36.185698 |
| 7 | `1,0` | 36.994669 |
| 8 | `0,1` | 36.002897 |

The accepted `1,0` order averaged `36.3890 tok/s`; reversed `0,1` averaged
`36.2829 tok/s` (`-0.292%`). Each order received one unrelated transient near
37 tok/s, and the complementary bracket did not reproduce an ordering gain.
The published `level_zero:1,0` selector remains unchanged.

## Symmetric reduce-scatter/all-gather: rejected as unsafe

A default-off prototype attempted to remove the fixed-root remote write while
retaining exact FP32 arithmetic. Rank 0 reduced the first 2,560 values and
rank 1 the second 2,560 into persistent local communicator buffers; each
finish kernel would then consume one local and one peer half. Two-float loads
kept 1,280 work-items per half, and peer-consumer events guarded the next
buffer overwrite without extra barrier submissions.

The first bounded `p0/n1` smoke hung at the first candidate collective before
producing a benchmark row. Both cards remained normal and the kernel log had
no Xe fault, reset, hangcheck, or device-lost report. A second build moved the
64 KiB-per-card scratch allocation into communicator initialization, before
any graph work, and added a marker after all four candidate submissions. The
second bounded smoke again stalled before that marker. It was terminated
before the driver timeout and again left both GPUs normal.

This isolates the failure from allocation and identifies bidirectional
cross-context event fan-in during submission as incompatible with this Level
Zero queue topology. The candidate was removed without a throughput or
quality claim. Future collective designs on this host must keep a single
logical dependency root; this symmetric scheduling shape must not be retried
unchanged.

## PCIe Max Read Request sizing: rejected

Both B70 endpoints normally expose Device Control word `0x2937`, including a
512-byte Max Read Request (MRRS), while their external links are healthy PCIe
5.0 x16. Since logical rank 0 performs the peer reads, endpoint-only MRRS was
tested as a reversible system-level candidate. ACS and bridge-routing bits
were not changed. Each write preserved every non-MRRS Device Control bit, was
read back before the workload, and used an exit trap that restored `0x2937`
on both `0000:03:00.0` and `0000:e3:00.0`.

Safety smokes passed at 1024, 2048, and 4096 bytes with both cards normal,
the expected fusion census, and `VERIFY_MISMATCH=0`. A symmetric
`p64/n256/r3` width screen measured:

| MRRS | Decode observations (tok/s) | Mean |
| ---: | --- | ---: |
| 512 B | 35.942004, 36.242550 | 36.092277 |
| 1024 B | 35.975401, 36.119281 | 36.047341 |
| 2048 B | 36.966356, 36.602129 | 36.784243 |
| 4096 B | 36.112990 | 36.112990 |

The short 2048-byte signal was then tested with a longer `p64/n512/r3`
A-B-B-A bracket:

| Order | MRRS | Decode tok/s |
| ---: | ---: | ---: |
| 1 | 512 B | 36.494563 |
| 2 | 2048 B | 36.080431 |
| 3 | 2048 B | 36.988537 |
| 4 | 512 B | 36.984076 |

Stock 512 B averaged `36.739320 tok/s`; 2048 B averaged
`36.534484 tok/s` (`-0.558%`). Both arms followed the same alternating
low/high variance, so the short 2048-byte apparent win was not an MRRS effect.
No persistent PCIe configuration change is promoted. Both endpoint words are
restored to `0x2937`, and no AER, Xe fault/reset, or device-lost event occurred.

## Direct attention V projection-to-cache write: quality-exact, rejected

The accepted full-attention Q/V/K projection already combines all three Q8
MMVQ projections in one kernel, but its V result still passed through a
standalone FP32-to-F16 indexed `SET_ROWS` launch on every rank. An isolated
default-off experiment added a separately named triple kernel that preserved
all three graph-visible FP32 outputs and, for each V row, converted the same
FP32 reduction result with SYCL's automatic rounding mode directly into the
selected F16 KV-cache row. The accepted triple kernel remained textually
unchanged for the same-binary control.

The bounded `p0/n1` debug smoke positively proved the mechanism: all 64
attention triples fired, the 64 standalone V `SET_ROWS` calls fell to zero,
and `VERIFY_MISMATCH=0`. The fixed 12-prompt cold endpoint suite then passed
with every cache count zero and all 12 output hashes exactly equal to the
promoted target-only oracle. Its one-suite conventional median was
`35.990872 tok/s`, full-512 after-TTFT was `35.935402 tok/s`, and TTFT was
`181.397 ms`; these are validity/support numbers, not a promoted record.

The first long `p64/n512/r3` A-B-B-A bracket was confounded by the known
inner-position advantage:

| Position | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | control | 36.035099 |
| 2 | direct V-cache | 36.124268 |
| 3 | direct V-cache | 36.661102 |
| 4 | control | 36.173960 |

The complementary B-A-A-B bracket balanced every arm across every position:

| Position | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | direct V-cache | 36.004227 |
| 2 | control | 36.134862 |
| 3 | control | 36.954506 |
| 4 | direct V-cache | 36.187841 |

Across all eight runs, control averaged `36.324607 tok/s` and direct V-cache
averaged `36.244360 tok/s`, a `-0.221%` result. Eliminating the small cache
conversion launch does not repay the extra store path in the already fused
projection kernel, so the candidate is rejected and is not part of the
production snapshot. Raw evidence is retained as `vcache-fused-*` under the
pass-2 artifact directory. Both GPUs remained normal, with no new Xe/AER
fault, reset, or hang entry.

## Recurrent lazy-zero clear elimination: rejected as endpoint-inert

A decode census from `llama-bench` initially appeared to show 192 recurrent
`SCALE(0)` launches per token across both cards: one convolution-state clear
and one GDN-state clear for each of the 48 recurrent layers on each rank. A
default-off prototype, selected by `GGML_SYCL_FUSED_RS_LAZY_ZERO=1`, admitted
only an in-place FP32 zero scale whose allocation, element count, cache name,
and sole-row state matched the already strict direct conv/GDN state-I/O
pattern. The fused kernels could then initialize their register state to zero
instead of reading the cleared row.

The one-token `llama-bench` positive control worked as designed: the same
binary reported `lazy_zero_conv=0`, `lazy_zero_gdn=0` with the selector off and
`96/96` with it on, while every established fusion count remained equal and
`VERIFY_MISMATCH=0`. Both cards remained normal.

The production server census invalidated the performance premise. A 512-token
cold endpoint canary reproduced the promoted `817e19c0...` output hash, but
its shutdown counters were `lazy_zero_conv=0 lazy_zero_gdn=0`, so that run was
not accepted as a candidate quality result. Verbose scheduler output with
temporary pointer instrumentation then showed why: the steady-state server
decode graph retains the recurrent `SCALE` nodes structurally, but their
runtime tensors are zero-sized (`0K`). The executor already discards them via
`ggml_is_empty`; the 120 KiB and 3 MiB forms occur in reserve/warm-up/reset
graphs rather than the production decode loop. Eliminating them cannot raise
the endpoint record.

The candidate is rejected without a timing suite and is not part of the
promoted patch or reproduction recipe. Diagnostic artifacts are retained as
`lazy-zero-*` in the pass-2 artifact directory. This corrects the earlier
launch/traffic estimate: no approximately 157 MB-per-token production clear
traffic was available to remove.

## Forced XMX/MMA decode attention: rejected

The production attention dispatcher normally reserves its XMX/DPAS kernel for
at least 64 query rows. Target-only decode has one query row, so the accepted
path uses TILE. The existing diagnostic `GGML_SYCL_FATTN_MMA=2` mode removes
that floor and pads the single row to the 64-row MMA tile. It was screened on
the immutable accepted binary because a competitive result would also expose
a clean route to combine Q-side RoPE with MMA's FP16 staging kernel.

A `p64/n256/r3` A-B-B-A bracket measured `35.172770` and `35.343531 tok/s`
for the normal TILE controls versus `34.416654` and `35.256598 tok/s` for
forced MMA. The pooled result was `35.258151 tok/s` TILE and
`34.836626 tok/s` MMA, a `-1.195%` regression. Excluding each process's first
lower-throughput sample did not rescue it: the four steady TILE observations
averaged `36.864450 tok/s`, while forced MMA averaged `36.275650 tok/s`
(`-1.597%`). Padding 63 inactive query rows costs more than DPAS recovers.

Forced MMA remains a test-only mode and is not part of the reproduction
recipe. Any Q-RoPE fusion for target-only decode must preserve the TILE path.
Raw logs are retained as `fattn-mma2-screen-*` in the pass-2 artifact
directory.

## Decode TILE subgroup width 16: rejected

The existing SYCL TILE attention kernel accepts subgroup widths 16 and 32 for
the Qwen3.6 decode shape (`D=256`, one query row, GQA ratio 6).  Its unset
runtime default is 32.  Matthew Dodd's fork comments that width 16 can be
faster for some shapes, so `GGML_SYCL_FATTN_TILE_WARP=16` was tested against
the immutable accepted binary; no source or arithmetic-path change was
needed for this screen.

Two complementary `p64/n256/r3` brackets were run as A-B-B-A and B-A-A-B so
that each arm occupied every run position once.  The first sample from every
fresh process carried the usual startup cost, so the primary comparison pools
the remaining two steady samples per run:

| TILE subgroup | Runs | All-sample mean (tok/s) | Steady mean (tok/s) |
| ---: | ---: | ---: | ---: |
| 32 (control) | 4 | 35.232175 | 36.782200 |
| 16 | 4 | 35.158200 | 36.719300 |

The fully position-balanced steady result is `-0.171%` for width 16.  The
per-position deltas crossed over (`+2.583%`, `+0.058%`, `-2.344%`, and
`-0.917%`), confirming that the larger apparent wins in isolated runs were
run-order variation rather than a repeatable kernel gain.  The accepted
default width 32 remains unchanged, and no endpoint quality run was warranted.
Raw logs are retained as `fattn-tile-warp-screen-*` and
`fattn-tile-warp-complement-*` in the pass-2 artifact directory.

## Decode attention KV-split factor above four: rejected

The accepted TILE launcher automatically selected four parallel KV blocks for
the deployed decode shape (`D=256`, GQA 6, `ncols1=1`, `ncols2=6`, subgroup
32, six warps, `nbatch_fa=64`).  Its debug census reported 16 subslices, 32
cores, four resident workgroups per core, and four 64-row KV tiles at the
initial cache allocation.  The existing `GGML_SYCL_FATTN_PB` control was used
to test whether exposing more independent KV tiles could improve utilization
as decode depth increased.

A mirrored `p64/n256/r3` screen ran `PB=4,6,8,8,6,4`.  Pooling the two steady
samples after each process's startup sample gave:

| Parallel KV blocks | Runs | All-sample mean (tok/s) | Steady mean (tok/s) | vs PB4 |
| ---: | ---: | ---: | ---: | ---: |
| 4 (control) | 2 | 35.310367 | 36.881100 | -- |
| 6 | 2 | 34.945617 | 36.527225 | -0.959% |
| 8 | 2 | 35.308100 | 36.925200 | +0.120% |

PB6 crossed over sharply between its two runs (`37.0683` and `35.9862`
