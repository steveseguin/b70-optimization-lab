## Static Q8 MMVQ code-generation audit

The accepted `mmvq.cpp` device bundle was extracted without loading the model
or running a GPU workload. `sycl-post-link --split=kernel` isolated each entry
point, `llvm-spirv` translated the selected modules, and `ocloc` generated
BMG-G31 assembly. Host-local evidence is under:

`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/igc-mmvq-accepted-smallgrf`

The active reordered Q8 decode kernel is the fourth lambda from
`reorder_mul_mat_vec_q8_0_q8_1_sycl` (`mmvq_67` in the split inventory). Its
static result is:

| Property | Accepted Q8 decode kernel |
| --- | ---: |
| Platform / SIMD | Xe2 / SIMD16 |
| GRF mode | 128 |
| IGC instruction count | 101 |
| register allocator | `LOCAL_ROUND_ROBIN_BC_RA` |
| scratch load/store traffic | none |
| weight load | one `load.ugm.d32x4.a64` |
| activation load | one `load.ugm.d32x4.a64` |
| scale loads | two `load.ugm.d16u32.a64` |

The upstream-compatible narrow control compiled to 121 instructions and seven
UGM loads. The phase arm compiled to 146 instructions. The deliberate mutant
compiled one operand as `d32x3`, which also positively identifies the active
wide/default entry point rather than relying on lambda suffixes alone.

This closes two tempting but invalid directions:

1. The kernel is already in BMG's 128-GRF high-occupancy mode. Forcing large
   GRF cannot increase residency.
2. There is no spill/fill or fragmented Q8 payload left to repair. Both 16-byte
   lane payloads are already single transactions, matching the previously
   measured ~591 GB/s isolated weight stream.

Four offline vISA register-allocation overrides (`-nolocalraroundrobin`,
`-noroundrobin`, `-nolocalra`, and `-forceGlobalRA`) were accepted by `ocloc`
but produced byte-identical assembly and the same allocator. They are not
runtime candidates.

## Next bounded candidate

Pass 1's local-memory collective-to-Q8 handoff showed a repeat-confirmed
`+0.958%` timing signal, but the first implementation placed a runtime branch
inside the accepted RMS/MUL kernel. Even its selector-off arm then produced a
different quality canary, proving that the experiment perturbed the compiler's
numerically sensitive kernel rather than isolating the treatment.

The next candidate will put the local handoff in separately named kernels and
leave the accepted global-store/barrier/reread lambdas textually unchanged.
The selector-off arm must first reproduce the promoted output hash. The
candidate must then match that hash (and the fixed 12-prompt suite) before any
speedup can be promoted.
