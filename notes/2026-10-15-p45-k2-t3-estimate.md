# Packet45: three-position target verification estimate

2026-10-15. Read-only analysis; no build, device execution, model-weight read,
or change to packet45/packet44. **Verdict: DROP the full k=2 implementation
on the present evidence.** Estimate **T3 = 76 ms**, with a **72–95 ms planning
range** for the implementations described below. That gives **28.41 tok/s
centrally, 23.10–29.85 tok/s** with the requested equation. Even hiding all
6.668 ms of drafting gives only **30.90 centrally, 24.72–32.62 tok/s**.
These are modelled rates, not benchmarks or confidence intervals. An entirely
new temporal-M=3 kernel set could fall outside this range; the receipts do not
measure one. This is a decision against funding that full build without new
evidence, not a claim that k=2 is physically impossible.

The previous roofline study left the acceptance and verification cost open.
The diagnostic probe resolves acceptance, but the retained target evidence
does **not** establish fast three-position verification. In particular, neither
`rows4` nor `launch_extent=32` is a temporal batch dimension.

## What the prefill and K2 measurements actually measure

All 194 inspected `prefill-timings.jsonl` files are empty. Prompt work is in
the ordinary rank `timings.jsonl`: **one position per HALF**, not chunks of
three or 32. Each suite has prompt lengths
`67,65,71,90,77,60,87,64,68,61,83,69`; each rank has 850 fixture-0 rows.
The last prompt position requests the first output and is not fixture 0.
W2m has an 87-token prompt and 86 fixture-0 rows per rank, also single-position.

[rank.hpp:105–177](../experiments/own-xpu-runtime/stage2/packet45-merged3/rank.hpp#L105)
admits one position and executes its launch list.
At line 144, prompt rows skip `final.*`, logits and argmax; decode does not.
At line 169 the rounded `launch_extent` is **history/cache capacity**, not M.
[native_controller.hpp:63–95](../experiments/own-xpu-runtime/stage2/packet45-merged3/native_controller.hpp#L63)
overlaps the next known prompt position on rank0 with the current rank1 half.
Consequently, prompt tokens/second is a pipeline rate, not an M>1 GEMM rate.

The following are pooled per-position medians, in ms; decode uses position
>=100, non-speculative, non-cancelled rows. They are not the published
busy-ms-per-emitted-interval statistic.

Forward = prepare + enqueue + wait. HALF includes the command's remaining
readback/bookkeeping. Three-prompt span is r0 start at p to r1 completion at
p+2, for p>=16 within fixture 0. It includes live-pipeline dependencies and
MTP teacher forcing; it is a measured analogue, **not a measured T3 verifier**.
WS spans are 70.934–71.428 ms; W2m is 71.871 ms. Decode additionally needs
three output heads and runs at longer live history. The configured capacity
is 4096, but these requests do not have 4096 live tokens: the prompt and
128-token decode cover roughly 60–217 occupied positions. A truly full 4K
history is not measured here and must not inherit this estimate unchanged.

Rank0 issues 853 commands per prompt/decode half; rank1 issues 919 prompt,
927 decode. Prompt r0-completed to r1-started has median 1.321–1.563 ms.
That includes previous rank1 work and the teacher-forced draft body. After
both r0 and the prior rank1 command are complete, the residual to rank1 HALF
is only **0.01428–0.01458 ms**. This residual is the handoff/control allowance
used below. Input upload and output readback remain in the measured HALF
times; they are not subtracted again.

K2 has **no measured temporal M=2 or M=3 target kernel** in these tables.
[p28/registry.hpp:5–40](../experiments/own-xpu-runtime/stage2/packet45-merged3/p28/registry.hpp#L5)
defines `rows` as output neurons and `count=10` as routed expert slots.
[gemv_timing.cpp:56–85](../experiments/own-xpu-runtime/stage2/packet45-merged3/gemv_timing.cpp#L56)
allocates one input vector for dense/paired projection and ten selected
experts, with synthetic routes 0..9 and rotated banks. A group of neurons,
experts, or cache positions is not a group of target tokens.

## M scaling, routing, and reuse

**The observed three-position distinct-expert count cannot be recovered.**
The 96 suite archives retain 4,608 target `.routes.bin` hashes, each with a
120-byte extent, but no route IDs. These are final-request states, not three
consecutive position snapshots. The retained step fixtures are layer output
streams. The probe logs g1/g2, not target expert IDs. W2m is not a temporal
route trace either. The retention rule is explicit in
[suite.py:143–171](../experiments/own-xpu-runtime/stage2/packet45-merged3/suite.py#L143):
hash binary state, retain JSON text, then archive the inventory. Hashes cannot
be inverted into expert unions. No random routing distribution is represented
below as observed routing.

Each token selects ten distinct experts per layer from 512. Therefore a
three-position union U3 lies in **[10,30]**. As a labelled sensitivity only,
independent uniform sets give `512*(1-(1-10/512)^3)=29.418`.
Real adjacent-token routes are correlated, and autoregressive draft errors
can change them further. Ten, twenty and thirty are useful bounds/scenarios,
not estimates extracted from these receipts.

| Executed class / production shape | K2 M=1 cost | Three-position scaling with existing kernels | What a new lossless M=3 kernel could reuse |
|---|---:|---|---|
| GDN QKV, 10240x2560, Q6 / Q8 | .062396 / .057292 ms | Three calls; three dots per output | Weight fetch/dequantization, while preserving each dot's order |
| Target logits, 248320x2560, Q6 | 1.418073 ms | 4.254219 ms total | One weight pass; three independent reductions/output vectors |
| IQ2 paired gate/up, 10x(640x2560), P39 checks | .080416 ms/layer | .241248 ms/layer | Weight/dequant only for experts shared by inputs |

| IQ4 down/status, 10x(2560x640), P39 | .093437 ms/layer | .280311 ms/layer | Only shared experts; input vectors are different |

The P39 production expert paths take precedence over the bare GEMV entries.
Their per-half M1 proxies are **4.00914 ms r0 / 4.346325 ms r1**; three calls
cost **12.02742 / 13.038975 ms**. These sums are K2 proxies, not in-pipeline
GPU profiling. No measured M3 acceleration factor exists. The table preserves
that distinction rather than interpreting a smaller expert union as a
proportional reduction of all arithmetic.

## T3 model and forecast

The cheapest implementable verifier uses existing exact kernels on three
known inputs and pipelines the two cards. Let A and B be the non-speculative
rank HALF durations, h the handoff allowance. For each position:

```
end0[i] = end0[i-1] + A
end1[i] = max(end0[i] + h, end1[i-1]) + B
T3 = A + B + 2*max(A,B) + h
```

This includes filling/draining the pipeline. `max(3*A,3*B)` would incorrectly
remove the initial dependency. `3*(A+B)` would incorrectly remove inter-card
overlap. One CCS per card prevents simultaneous target and draft compute on
rank1. Copies may overlap subject to their real dependencies.

| Evidence used | r0 work for 3 positions | r1 work for 3 positions | Pipelined T3 |
|---|---:|---:|---:|
| SPEED6 cards01 | 53.122 ms | 58.230 ms | 75.951 ms |
| SPEED6 cards23 | 53.074 ms | 57.923 ms | 75.629 ms |
| SPEED7 cards01 | 52.996 ms | 58.297 ms | 75.976 ms |
| SPEED7 cards23 | 52.955 ms | 57.964 ms | 75.630 ms |

Thus the central estimate rounds to **76 ms**. The lower planning edge,
**72 ms**, generously rounds down the forward-only version (about73 ms),
removing most command overhead. The upper edge, **95 ms**, covers a
different implementation: process all three rows on rank0, then all three
on rank1, amortizing weight reads but losing row streaming. It is not a
statistical interval for a kernel that has never run.

For that blocked implementation, subtracting two dense weight passes from
three measured HALF calls at the lab's optimistic **600 GB/s** read rate
gives **45.510 ms r0 + 47.437 ms r1 + .014 ms = 92.962 ms**, for U3=30.
At U3=20 it is91.379 ms; even identical routes U3=10 gives89.796 ms.
This additive byte-subtraction model assumes all other instruction/launch
costs persist; it is not a lower bound on a completely redesigned M3 kernel.
Bandwidth is grounded in [packet7's measured ceiling](../experiments/own-xpu-runtime/stage2/packet7-kopt2/receipts-card3-20261011/ceiling/native.json),
590–600 GB/s; it is not an assumed advertised specification.
Unbatched, unpipelined verification would be111.35 ms, worse than the range.

The probe gives p1=.7867454068, q2=.7139282736, E=2.3484251969 and
D1+D2=6.668145 ms. Use paired outcomes, not consecutive one-step hits.
T3 must be below52.903279 ms without drafting overlap, or below59.571424 ms
even with **all** drafting hidden, to beat39.422009. A 5% gain without overlap
requires T3 about50.07 ms. Saving only memory/launch costs on the draft does
not remove this verifier requirement.

| T3 scenario | Requested equation, tok/s | Entire draft hidden, optimistic tok/s |
|---|---:|---:|
| 48 ms, reopening target; not measured | 42.96 | 48.93 |
| 52.903 ms, break-even | 39.42 | 44.39 |
| 60 ms, aggressive unproven improvement | 35.23 | 39.14 |
| 72 ms, lower planning edge | 29.85 | 32.62 |
| **76 ms, central** | **28.41** | **30.90** |
| 95 ms, upper planning edge | 23.10 | 24.72 |

Some draft overlap is legal: rank0 can process the already-known first input
while rank1 makes g1/g2. A>=17.65 ms exceeds D1+D2, so completely hiding D is
a useful *upper scenario* if the next two inputs are ready when needed.
It is not compute/compute overlap on rank1. Across renewal boundaries,
target hidden state and accepted-prefix selection still constrain the next
draft; do not claim an additional free verifier half.

Early rejection cannot rescue the unchanged-kernel schedule in this model.
Even with instantaneous cancellation of all unnecessary suffix work, its
expected verifier time is `A+B+h+(p1+p1*q2)*max(A,B)` = **63.304 ms**.
That predicts33.56 tok/s with D serialized, or **37.10 tok/s with D entirely
hidden**, before recovery. This is an alternative expected-time calculation,
not the fixed-T3 formula or a measured cancellation implementation.

All forecasts omit new prefix-restoration overhead, target-to-MTP cache
reanchoring, and extra arena pressure, which can only worsen these particular
schedules. The probe's64.10 ms backup and79.97 ms restore/check are diagnostic
isolation costs, not production D; they are correctly excluded. A production
k2 implementation must replace their function safely, not just delete it.
Likewise, the current rank1 target never speculates; accepting only a prefix
of three target positions needs a new rank1 recovery proof. Its85.22 MiB
arena headroom is not permission for unbounded extra snapshots/workspaces.

The rates above apply the requested pooled renewal equation. They are not
the exact class-balanced99-interval statistic; class-specific acceptance,
duration correlation and boundary costs would be needed for that forecast.
This limitation cannot turn the roughly28–31 tok/s central estimate into a
credible record prediction.

## Decision and the evidence that could reopen it

**DROP the full k=2 controller/verifier build now.** The new acceptance is
real, but the retained prefill/K2 evidence supplies neither temporal M3
speedup nor observed route sharing sufficient to forecast a win. Repeated
M1 execution and a small controller change are not enough. The earlier
roofline was a physical opportunity, not a forecast that batched kernels
already existed.

If independently justified M3 kernel work later warrants one measurement,
the cheapest decisive experiment is diagnostic-only: admit the production
23/25 plans, seed an actual suite prefix, run three target inputs with all
three heads enabled, and measure rank0/rank1 events plus first-input-to-last-
logit wall time. Compare all three logits/argmax and every accepted-prefix
state against three serial exact calls. Record actual ten-ID routes per
layer/position, so U3 becomes measured. Test both correct guesses and first/
second rejection; preserve state/cache/bank/error rules and the arena cap.
Use representative prefix lengths from these receipts, and separately label
any genuinely full4K test. It must never qualify as a speed submission.

A new result near **48 ms end-to-end T3**, with bounded recovery costs, would
justify reopening. Full scope would then be substantial: M3 dense/expert
execution preserving reduction order; ordered GDN/QSA state for three inputs;
controller acceptance of0/1/2 guesses plus bonus; prefix commit/rollback on
both ranks; two speculative-position images or equivalent checked undo;
MTP autoregressive hidden/embedding chaining and target-state reanchoring;
memory/admission, mini full-state negative controls, and device oracle suites.
None of that work or a device experiment was launched by this analysis.
