# Packet58am demand-transfer preparation

Review 38 authorized building the one-card demand-transfer candidate before
the census verdict. The parent is packet58ah chain b, the full 31.663 tok/s
composition. Packet58aj contributes cold-start evidence only. Packet58al's
decision document is unchanged.

The new packet keeps separate demand-copy ownership, a fixed two-bank staging
pool and original-slot outputs. A retained stage can replace the source of an
ordinary later cache fill only after revocation, and stays leased until that
fill completes. It does not become an extra cache for later tokens.

GNU and Intel compile the runtime. The synthetic real-shape byte checks run
twice per compiler, comparing every retained output/intermediate/status byte.
The mask and lease checks cover all 1,024 masks at all 48 layers. The real
device binary's CPU-only entry probe runs the smoke and five-view arguments
through loading metadata, preparation and first decode; syscall traces check
for model/device opens. These are CPU proofs, not device quality results.

The analyzer replays all twelve real parent requests, retaining the cold first
prefill token at 23,457.6 ms and the first request's 28,124.118482 ms prefill.
Corrupt/missing identity, token and event fixtures fail. The largest inspected
cold enclosing stage is 219,549.898057 ms, so the first operation wait is 879
seconds. No elapsed-time threshold decides whether a data stream is valid.

The prepared allocation ledger keeps the fixed stage pool and maps within the
existing transfer allowance. Host admission remains 99,119,554,560 bytes with
the full 8 GiB reserve. The smoke and v5 storage reservations are based on
actual parent artifact sizes plus separately labeled serialized synthetic
event records; v5 requires a refresh using real smoke volume.

The proposals contain K1 and native command arrays, fresh names and the
coordinator's admission requirements. Nothing was launched or queued. The
coordinator applies the existing whole-host window protocol to these inert
specifications. A timing hold interrupted CPU preparation; the compile helper
waited until it released. No GPU, service, sudo, host setting or existing packet
was changed by this preparation.

Readiness stays false until the packet58ai census has a complete valid bound
of at least 1.000 ms/token. The same-parent smoke must then prove exactness and
useful overlap before v5. All final hashes and proof status are in
[the packet](../experiments/own-xpu-runtime/stage2/packet58am-demand-transfer/README.md),
its build receipt, seal and final readiness marker. No speedup is claimed.
