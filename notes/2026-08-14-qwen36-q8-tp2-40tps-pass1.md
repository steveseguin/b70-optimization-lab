# Qwen3.6 27B Q8 TP2 target-only optimization: pass 1

Date: 2026-08-14  
Host: 2x ASRock Intel Arc Pro B70, 32 GiB per card  
Scope: conventional target-only decode; no MTP, DFlash, or other speculation

## Starting point

The accepted reproduction snapshot is commit `ce51350b8` and reports:

- 35.699225 tok/s conventional endpoint median
- 36.059823 tok/s legacy-compatible endpoint median
- about 36.6 tok/s in longer direct `llama-bench` repeats
- 42.5 tok/s approximate aggregate HBM roofline for the 28.596 GB Q8 model

The optimization work is isolated on branch `agent/qwen36-q8-tp2-40tps`. The accepted source/build remains the recovery reference while candidates use separate source and build paths.

## Hardware topology

`xpu-smi topology -m` reports `SYS` between GPU 0 and GPU 1. The cards share the same CPU affinity but traverse different PCIe host bridges. This makes per-token TP collective latency a first-class constraint; branding and cooling do not change that interconnect.

## Profiler rejection and recovery

The llama.cpp built-in `GGML_SYCL_PROFILE=1` path was tried once at `p64/n16`. It inserts device-wide timing barriers and is not production-equivalent. On this host it caused Level Zero `UR_RESULT_ERROR_DEVICE_LOST`, CAT/fault messages, and engine resets on both cards. It must not be retried.

Both devices returned to `Device State: normal` immediately after the reset. A normal, unprofiled target-only `p64/n16/r1` smoke then passed at:

- prompt processing: 384.738573 tok/s
- token generation: 35.395890 tok/s

The short `n16` result is only a recovery check, not a headline benchmark. Raw logs are retained outside Git in:

- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/profile-current-p64-n16.log`
- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/post-reset-smoke-p64-n16.log`

## Current direction

Further measurements will use low-intrusion `xpu-smi dump` sampling during ordinary unprofiled runs. Candidate changes must pass matched reversed-order A/B tests and exact output/quality gates before promotion.

Already-rejected experiments will not be recycled as new work. These include root-barrier elision, Q8 scale broadcast, Q8 cache, VDR2/VDR8, the earlier column-split/block-remap attempt, and broad subgroup/workgroup sweeps. The next useful question is whether the remaining gap is predominantly HBM efficiency, cross-bridge collective latency, or host submission overhead.

## Ordinary-run telemetry

An uninstrumented `p64/n512/r1` run reached `35.862770 tok/s`. During its decode window both cards held their full `2,800 MHz` graphics clock. Average card power was about `181.86 W` and `188.58 W`, comfortably below the `275 W` limit. This rules out thermal, clock, and board-power throttling as the immediate limiter. The installed `xpu-smi` build returned `N/A` for HBM, EU, and PCIe throughput counters, so those unavailable fields are not interpreted.

## Safe graph census and first candidate

A count-only `p0/n1` census—without device timestamps or profiling barriers—confirmed `128` allreduces per token. All `128` reached the fused allreduce+residual+RMS+multiply path. The remaining Q8 matrix-vector shapes were the expected per-rank `3072x5120` and `8704x5120` families plus the `5120x124160` output head.

The first source candidate is an opt-in dual-peer RMS reduction in the isolated `/mnt/fast-ai/src/llama.cpp-q8-tp2-40tps` tree. The incumbent path runs one root-GPU reduction kernel, then releases one RMS/Q8 kernel on each card. The candidate removes the root launch: each card independently reads the other 20 KiB partial and performs the ordered `p0+p1`, residual add, RMS, multiply, and Q8 handoff locally. It is disabled by default behind `GGML_SYCL_COMM_DUAL_PEER_RMS=1` and will be discarded unless matched throughput and exact-output gates pass.

### Dual-peer RMS result: rejected

The isolated candidate compiled successfully with the pinned oneAPI 2026.1 BMG-G31 AOT configuration. Its final `llama-bench` link initially failed because the constrained build process no longer had the Intel compiler-library path in `LD_LIBRARY_PATH`; re-linking under the same pinned component environments succeeded without recompiling the GPU library. Peak build pressure stayed bounded at 3.0 GiB RAM plus 311 MiB swap.

The candidate passed `p0/n1` and `p64/n16` safety smokes, produced no reported verification mismatch, and left both GPUs in the normal state. A same-binary `A-B-B-A` screen then used `p64/n256/r3`, where `A` disabled and `B` enabled `GGML_SYCL_COMM_DUAL_PEER_RMS`:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | control, off | 35.875535 |
| 2 | dual-peer, on | 35.655327 |
| 3 | dual-peer, on | 35.596090 |
| 4 | control, off | 35.734405 |

The two-arm means were 35.804970 tok/s control and 35.625709 tok/s candidate, a `-0.501%` regression. Duplicating the reduction on both cards costs more than the root-to-peer dependency it removes. The door remains default-off and is not promoted; a full endpoint quality suite is unnecessary for a clearly negative speed candidate.

Raw logs are retained outside Git under `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/dualpeer-*`.

## Root-fused follow-ups: rejected

Two lower-traffic variants were compiled together under the same pinned AOT configuration. The incremental build peaked at 3.2 GiB RAM, used no swap, and completed normally.

The conservative `GGML_SYCL_COMM_ROOT_FUSED_RMS=1` arm kept one root reduction but folded it into rank 0's RMS/Q8 kernel. Rank 1 then depended on that longer root kernel. Its `p0/n1` smoke was already slower at 34.637222 tok/s, versus the post-reset accepted control's 35.272304 tok/s. This serialization is the wrong scheduling shape and no long screen was warranted.

The aggressive `GGML_SYCL_COMM_ROOT_BOTH_RMS=1` arm tried to produce both ranks' residual/RMS/Q8 outputs in one root kernel, followed by a rank-1 dependency barrier. It is unsafe and must not be retried. Its first `p0/n1` smoke made an invalid remote-memory access on GPU 0, producing `UR_RESULT_ERROR_DEVICE_LOST`, Xe page faults/CAT errors, and a timed-out compute job. The kernel driver completed an automatic GT reset at 10:13:06 EDT. A known-good accepted-binary `p0/n1` run was then repeated inside the production-equivalent 10 GiB memory ceiling and passed at 35.272304 tok/s with both GPUs normal.

The failed arm also demonstrated why every remaining benchmark on this 16 GiB host must use a bounded systemd cgroup. An uncapped recovery attempt grew to 13.8 GiB RSS while the driver was still timing out; it was terminated before the desktop became unresponsive. The capped recovery peaked near 8.0 GiB cgroup memory with light swap and completed normally.

Raw evidence:

- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/root-fused-smoke-p0-n1.log`
- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/root-both-smoke-p0-n1.log`
- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/post-auto-reset-control-p0-n1.log`

The next candidate reuses the in-order queues' existing last events instead of submitting two readiness barriers at each of the 128 fused collectives per token. This preserves all tensor math and has an unchanged barrier fallback. An independent TP4 B70 lane measured a 3.462% exact-output win from the same runtime technique; Qwen TP2 still requires its own matched test.

### Last-event readiness result: neutral/rejected

`GGML_SYCL_COMM_LAST_EVENT_READY=1` passed its bounded `p0/n1` smoke at 35.392835 tok/s and produced no new driver error. The same-binary `p64/n256/r3` A-B-B-A result was:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | barrier control | 35.649774 |
| 2 | last event | 35.630718 |
| 3 | last event | 35.630854 |
| 4 | barrier control | 35.637613 |

The pooled controls averaged 35.643694 tok/s and the candidate averaged 35.630786 tok/s, or `-0.036%`. This is stable neutrality rather than a transferable win. The specialized TP2 fused communicator's two readiness barriers evidently do not carry the same host-submission cost as the generic TP4 recursive-doubling path. The door is not promoted and no endpoint quality run is warranted.

All four arms ran inside one 10 GiB maximum-memory cgroup. It peaked at 8.0 GiB accounted memory and 134 MiB swap; both GPUs remained normal and no post-reset faults appeared. Raw logs are retained as `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/lastevent-abba-*`.

## Matthew's reorder and deep-batch settings: neutral for target-only decode

Matthew subsequently suggested `GGML_SYCL_REORDER_IN_GEMM=1`,
`GGML_SYCL_FORCE_REORDER=1`, `-b 8192`, and `-ub 2048`. These are relevant
to deep prefill and multi-column verification, but the question here is
steady-state target-only `ne[1]=1` decode. A same-binary capped A-B-B-A screen
compared that complete setting bundle against the promoted `-b 1024 -ub 256`
configuration at `p64/n256/r3`:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | promoted control | 35.758743 |
| 2 | reorder flags + 8192/2048 | 36.386565 |
| 3 | reorder flags + 8192/2048 | 35.810393 |
| 4 | promoted control | 36.484249 |

The pooled controls averaged 36.121496 tok/s and the suggested settings
averaged 36.098479 tok/s, or `-0.064%`. The apparent first-treatment spike was
run-order drift: the closing control was faster still. These settings are not
promoted for target-only decode.

The count-only MUL_MAT census prints equal ordinary and reordered Q8 rows in a
one-token process because it records the pre-dispatch tensor state: each weight
is ordinary on its first call, gets reordered lazily inside that call, and is
reordered on the later call. It does **not** mean one TP rank remains on the
ordinary kernel. Raw logs are retained as
`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/matt-config-*`.

## True SIMD32 Q8 decode: rejected in the fused graph

The earlier subgroup-count bracket changed the number of SG16 subgroups per
workgroup; it did not exercise the separate `GGML_SYCL_MMVQ_SG32=1` kernel.
That true SIMD32 path had shown a small B70 win in an older, less-fused model
run, so it received a capped `p64/n256/r3` A-B-B-A screen here:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | SG16 control | 35.709024 |
| 2 | SIMD32 | 34.007060 |
| 3 | SIMD32 | 34.012612 |
| 4 | SG16 control | 36.510009 |

The pooled controls averaged 36.109517 tok/s and SIMD32 averaged 34.009836
tok/s, a `-5.814%` regression. The SIMD32 launcher deliberately refuses the
pair/triple/quad fused MMVQ paths, so its standalone row-kernel improvement
does not survive this graph's more valuable launch fusions. It remains off.
Raw logs are retained as
`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/sg32-*`.

## Same-subgroup FFN dual-row kernel: rejected

An opt-in experimental kernel computed matching rows of the two equal-size
FFN gate/up Q8 matrices in one subgroup. It shared the Q8_1 activation load
and addressing, retained the incumbent per-output FP32 accumulation order,
and halved row scheduling without disabling any graph fusion. Its capped
`p0/n1` safety smoke passed at 36.148692 tok/s; all expected fused-pair census
hits remained live, both GPUs stayed normal, and no new Xe error was logged.

The same-binary `p64/n256/r3` A-B-B-A result was:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | incumbent pair | 35.908037 |
| 2 | dual-row pair | 35.709207 |
| 3 | dual-row pair | 36.436764 |
| 4 | incumbent pair | 36.577945 |

The pooled controls averaged 36.242991 tok/s and the candidate averaged
36.072986 tok/s, a `-0.469%` regression. Halving the scheduled subgroups cost
slightly more memory concurrency than the shared activation work recovered.
The candidate is rejected. Raw logs are retained as
`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/dualrow-*`.

## Alternating TP2 reduction roots: rejected

The accepted fused collective always runs its 20 KiB `p0 + p1` reduction on
rank 0. An opt-in candidate alternated that same ordered reduction between
ranks while retaining the existing dependency barriers and both local
RMS/multiply/Q8 kernels. This was deliberately narrower than the unsafe
one-root/two-output experiment: the odd root wrote only the same reduction
state that the incumbent root writes in the opposite direction.

The capped `p0/n1` smoke passed at 36.117156 tok/s. Both reverse peer access
and the full fusion census completed, both GPUs stayed normal, and there was
no new Xe fault/reset. The same-binary `p64/n256/r3` A-B-B-A result was:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | fixed rank-0 root | 35.792540 |
| 2 | alternating root | 35.853041 |
| 3 | alternating root | 35.635922 |
| 4 | fixed rank-0 root | 36.544914 |

The pooled fixed-root controls averaged 36.168727 tok/s and the alternating
candidate averaged 35.744482 tok/s, a `-1.173%` regression. The PCIe/topology
direction chosen by the incumbent is materially better; rank 0 remains the
fixed reduction root. Raw logs are retained as
`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/alternate-root-*`.

## Interleaved fused-FFN row scheduling: rejected as neutral

The rejected dual-row experiment had halved the number of scheduled
subgroups, so a narrower opt-in variant retained the incumbent subgroup count
and exact SG16 row arithmetic while alternating equal-size gate/up matrix rows
across the existing fused launch. This tested whether mixing the two weight
streams improved B70 HBM/workgroup scheduling without changing any output's
FP32 accumulation order. Its capped `p0/n1` smoke passed at 36.262205 tok/s;
both devices remained normal and no new Xe error appeared.

An initial same-binary `p64/n256/r3` A-B-B-A screen looked weakly favorable:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | sequential-row control | 35.698157 |
| 2 | interleaved rows | 36.555678 |
| 3 | interleaved rows | 36.542439 |
| 4 | sequential-row control | 36.568851 |

The pooled candidate was 36.549059 tok/s versus 36.133504 for control
(`+1.150%`), but that entire apparent gain depended on the unusually slow
opening control. A longer reversed-order `p64/n512/r3` B-A-A-B drift check
did not confirm it:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | interleaved rows | 35.853967 |
| 2 | sequential-row control | 35.971639 |
| 3 | sequential-row control | 36.360188 |
| 4 | interleaved rows | 36.387096 |

At the longer decode depth, the pooled candidate averaged 36.120532 tok/s and
control averaged 36.165914 tok/s, or `-0.126%`. Interleaving is therefore
neutral-to-negative and is not promoted. Raw logs are retained as
`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/interleave-*`.
