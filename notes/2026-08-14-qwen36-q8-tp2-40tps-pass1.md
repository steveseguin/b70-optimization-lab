# Qwen3.6 27B Q8 TP2 target-only optimization: pass 1

Date: 2026-08-14  
Host: 2x ASRock Intel Arc Pro B70, 32 GiB per card  
Scope: conventional target-only decode; no MTP, DFlash, or other speculation

## Starting point

The accepted reproduction snapshot is commit `ce51350b8` and reports:

- 35.699225 tok/s conventional endpoint median
- 36.059823 tok/s legacy-compatible endpoint median
- about 36.6 tok/s in longer direct `llama-bench` repeats
- 42.5 tok/s approximate aggregate HBM roofline for the 28.596 GB Q8 model

The optimization work is isolated on branch `agent/qwen36-q8-tp2-40tps`. The accepted source/build remains the recovery reference while candidates use separate source and build paths.

## Hardware topology

`xpu-smi topology -m` reports `SYS` between GPU 0 and GPU 1. The cards share the same CPU affinity but traverse different PCIe host bridges. This makes per-token TP collective latency a first-class constraint; branding and cooling do not change that interconnect.

## Profiler rejection and recovery

The llama.cpp built-in `GGML_SYCL_PROFILE=1` path was tried once at `p64/n16`. It inserts device-wide timing barriers and is not production-equivalent. On this host it caused Level Zero `UR_RESULT_ERROR_DEVICE_LOST`, CAT/fault messages, and engine resets on both cards. It must not be retried.

Both devices returned to `Device State: normal` immediately after the reset. A normal, unprofiled target-only `p64/n16/r1` smoke then passed at:

- prompt processing: 384.738573 tok/s
- token generation: 35.395890 tok/s

The short `n16` result is only a recovery check, not a headline benchmark. Raw logs are retained outside Git in:

- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/profile-current-p64-n16.log`
- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/post-reset-smoke-p64-n16.log`

## Current direction

Further measurements will use low-intrusion `xpu-smi dump` sampling during ordinary unprofiled runs. Candidate changes must pass matched reversed-order A/B tests and exact output/quality gates before promotion.

Already-rejected experiments will not be recycled as new work. These include root-barrier elision, Q8 scale broadcast, Q8 cache, VDR2/VDR8, the earlier column-split/block-remap attempt, and broad subgroup/workgroup sweeps. The next useful question is whether the remaining gap is predominantly HBM efficiency, cross-bridge collective latency, or host submission overhead.

## Safe graph census and first candidate

A count-only `p0/n1` census—without device timestamps or profiling barriers—confirmed `128` allreduces per token. All `128` reached the fused allreduce+residual+RMS+multiply path. The remaining Q8 matrix-vector shapes were the expected per-rank `3072x5120` and `8704x5120` families plus the `5120x124160` output head.

The first source candidate is an opt-in dual-peer RMS reduction in the isolated `/mnt/fast-ai/src/llama.cpp-q8-tp2-40tps` tree. The incumbent path runs one root-GPU reduction kernel, then releases one RMS/Q8 kernel on each card. The candidate removes the root launch: each card independently reads the other 20 KiB partial and performs the ordered `p0+p1`, residual add, RMS, multiply, and Q8 handoff locally. It is disabled by default behind `GGML_SYCL_COMM_DUAL_PEER_RMS=1` and will be discarded unless matched throughput and exact-output gates pass.

### Dual-peer RMS result: rejected

The isolated candidate compiled successfully with the pinned oneAPI 2026.1 BMG-G31 AOT configuration. Its final `llama-bench` link initially failed because the constrained build process no longer had the Intel compiler-library path in `LD_LIBRARY_PATH`; re-linking under the same pinned component environments succeeded without recompiling the GPU library. Peak build pressure stayed bounded at 3.0 GiB RAM plus 311 MiB swap.

The candidate passed `p0/n1` and `p64/n16` safety smokes, produced no reported verification mismatch, and left both GPUs in the normal state. A same-binary `A-B-B-A` screen then used `p64/n256/r3`, where `A` disabled and `B` enabled `GGML_SYCL_COMM_DUAL_PEER_RMS`:

## Root-fused follow-ups: rejected

Two lower-traffic variants were compiled together under the same pinned AOT configuration. The incremental build peaked at 3.2 GiB RAM, used no swap, and completed normally.

The conservative `GGML_SYCL_COMM_ROOT_FUSED_RMS=1` arm kept one root reduction but folded it into rank 0's RMS/Q8 kernel. Rank 1 then depended on that longer root kernel. Its `p0/n1` smoke was already slower at 34.637222 tok/s, versus the post-reset accepted control's 35.272304 tok/s. This serialization is the wrong scheduling shape and no long screen was warranted.

The aggressive `GGML_SYCL_COMM_ROOT_BOTH_RMS=1` arm tried to produce both ranks' residual/RMS/Q8 outputs in one root kernel, followed by a rank-1 dependency barrier. It is unsafe and must not be retried. Its first `p0/n1` smoke made an invalid remote-memory access on GPU 0, producing `UR_RESULT_ERROR_DEVICE_LOST`, Xe page faults/CAT errors, and a timed-out compute job. The kernel driver completed an automatic GT reset at 10:13:06 EDT. A known-good accepted-binary `p0/n1` run was then repeated inside the production-equivalent 10 GiB memory ceiling and passed at 35.272304 tok/s with both GPUs normal.

The failed arm also demonstrated why every remaining benchmark on this 16 GiB host must use a bounded systemd cgroup. An uncapped recovery attempt grew to 13.8 GiB RSS while the driver was still timing out; it was terminated before the desktop became unresponsive. The capped recovery peaked near 8.0 GiB cgroup memory with light swap and completed normally.

Raw evidence:

- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/root-fused-smoke-p0-n1.log`
- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/root-both-smoke-p0-n1.log`
- `/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/post-auto-reset-control-p0-n1.log`

The next candidate reuses the in-order queues' existing last events instead of submitting two readiness barriers at each of the 128 fused collectives per token. This preserves all tensor math and has an unchanged barrier fallback. An independent TP4 B70 lane measured a 3.462% exact-output win from the same runtime technique; Qwen TP2 still requires its own matched test.

## Coarse unequal tensor split: strongly rejected

Because rank 0 owns the fused collective reduction, a capped split-ratio
screen tested whether moving a small amount of Q8 weight traffic off that
rank would shorten the TP2 critical path. The accepted binary and all runtime
settings were held fixed; only `-ts` changed. Opening and closing 50/50
controls bracketed both imbalance directions:

| Order | Tensor split | Decode tok/s |
| ---: | ---: | ---: |
| 1 | 0.50/0.50 | 35.513486 |
| 2 | 0.48/0.52 | 33.502241 |

| 5 | 0.54/0.46 | 32.508220 |
| 6 | 0.50/0.50 | 35.698995 |

count, and reduction order remained unchanged. The candidate was applied to
the direct and fused pair/triple/recurrent Q8 paths. Its capped `p0/n1` smoke
passed at 35.724793 tok/s; both devices remained normal and no new Xe error
appeared.

## Fused gate/up + SwiGLU + Q8 epilogue: rejected

A read-only GDB inventory established that each decode FFN graph is exactly
four nodes with distinct, non-overlapping buffers:

1. `ffn_gate` Q8 MMVQ, 8704 outputs;
2. `ffn_up` Q8 MMVQ, 8704 outputs;
3. SwiGLU over gate/up;
4. Q8 `ffn_down` MMVQ over the SwiGLU result.

An opt-in combined kernel therefore computed matching gate/up rows in each
subgroup, preserved the stock FP32 MMVQ store/reload boundary, produced the
SwiGLU F32 output, and populated the exact reordered Q8_1 memo consumed by the
down projection. One 512-work-item workgroup owned each 32-row Q8 block. Its
first subgroup reproduced the incumbent two-values-per-lane Q8 scale and sum
reduction order before all subgroup leaders wrote the quantized bytes. The
graph executor skipped the standalone SwiGLU node only after successfully
reserving that node's dedup buffer.

The capped `p0/n1` smoke passed at 35.086898 tok/s. The census retained all
expected 256 FFN pair and 256 SwiGLU-Q8 producer hits, both GPUs remained
normal, and no new Xe fault appeared. A same-binary `p64/n256/r3` A-B-B-A
screen was noisy:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | separate SwiGLU control | 35.684255 |
| 2 | combined epilogue | 35.464182 |
| 3 | combined epilogue | 36.387595 |
| 4 | separate SwiGLU control | 35.717604 |

The candidate appeared `+0.630%` only because its second arm drifted sharply.
A reversed, longer `p64/n512/r3` B-A-A-B gate rejected it:

| Order | Arm | Decode tok/s |
| ---: | --- | ---: |
| 1 | combined epilogue | 35.457322 |
| 2 | separate SwiGLU control | 36.327391 |
| 3 | separate SwiGLU control | 35.847349 |
| 4 | combined epilogue | 36.323829 |

The long controls averaged 36.087370 tok/s and the candidate averaged
35.890576 tok/s, or `-0.545%`. Removing the separate SwiGLU/Q8 launch roughly
offsets, but does not overcome, the matching-row concurrency and workgroup
barrier cost. This geometry is rejected without a quality-suite promotion.
Raw logs and the GDB graph capture are retained under
`/mnt/fast-ai/bench-results/qwen36-q8-asrock-b70-20260814-40tps/` as
`pair-swiglu-*` and `gdb-ffn-graph.log`.
