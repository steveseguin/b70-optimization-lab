# October 17 — screen v4, CPU preparation

V4 is prepared and sealed for new packets. It stops its own ranks even when the
shared teardown gate refuses, and releases a completed lane before CPU reports
or final validators run. Existing packets, screen versions and ops files were
not changed. No GPU, model, service, sudo operation or host setting was used.
The live chain remains with the coordinator, so CURRENT.md's live-state claims
are unchanged.

The owner reported that packet67's lane-B screen finished its suite at 19:28,
then encountered packet70 K2's stale teardown record at 19:33. Its gate raised
before the stop call, leaving two idle ranks resident for 36 minutes. The
coordinator's cooperative stop-pipe write drained them in seven seconds. These
are supplied incident facts, not a device test run by this task.

[The new wrapper](../experiments/own-xpu-runtime/stage2/screen/v4-lanes/README.md)
copies v3-packet64-lanes and ports packet70's private lease-before-report change
and regression tests. The new refusal callback runs while the shared flock is
still held. It sends the existing `!` stop through only that worker's transport
and uses its existing 65-second bounded close. It then raises the original
refusal and writes a local false drain record with the reason. It never clears
another lane's shared record. An owner that cannot exit stays supervised for
the coordinator; no hard kill or automatic restart was added.

Final report-input validation and aggregation now run after the parent confirms
drain, worker exit, process identity, client checks and fresh postflight, then
releases both the cooperative reservation and the legacy lane lock. CPU report
failures still fail the screen but leave no marker, latch or incomplete drain.
Per-request exactness and the 13-request sequence are unchanged.

All **103 CPU tests pass**, including every inherited v3 lane test. The actual
transport stop/close methods drained two temporary pipe-polling CPU children
under the flock after an other-lane refusal, while a third child stayed alive.
Additional checks cover bad shared JSON, missing cooldown data, failed receipt
writes, bounded-drain failure, report/validator errors, and conservative
worker/drain/postflight failures. The original and new fake-transport request
receipts remain byte-identical.
