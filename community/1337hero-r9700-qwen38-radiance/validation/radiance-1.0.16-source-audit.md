## Decisive findings

1. **The target head's “exact rerank” is not exact full-vocabulary verification.** An INT2 approximation first chooses block candidates; the best 64 candidate scores are recomputed using original BF16/FP16 weights. Target mode makes every other token ineligible. Rescoring cannot recover a true winner omitted by the approximate shortlist. There is no per-input recall certificate or full-head fallback triggered by a potentially omitted winner. This is a source-derived risk, not a demonstrated failure on the submitted run. [Candidate selection and rerank implementation](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/radiance_drafthead.py#L108-L224)

2. **The target gate relies on empirical shortlist recall.** It enables the fast path for greedy requests (subject to batch size, grammar, and logprob conditions); the comment cites 8,192 captured inputs and eight completions. Sampled requests require top-k at most 16 for rerank 64 and min-p zero. The module itself acknowledges that correctness requires all true supported tokens to occur in the shortlist. These constraints are useful but do not prove that recall condition for unseen inputs. A sampled quality pass and deterministic repetition also do not establish exact output identity. [Target gate and stated conditions](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/radiance_verifyhead.py#L14-L54), [actual greedy gate](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/radiance_verifyhead.py#L154-L193)

3. **FAST_DRAFT is not necessarily draft-only in this image.** OCI defaults include `RADIANCE_FAST_DRAFT=0`, `RADIANCE_VERIFY_HEAD=1`, and `RADIANCE_DRAFT_RERANK=64`. Thus opting into FAST_DRAFT also permits the target shortcut unless VERIFY_HEAD is disabled or runtime gates decline it. The W4 drafter patch itself brackets only the drafter load using try/finally; reducing draft precision is a separate, potentially safe optimization when verification faithfully preserves the target. Do not conflate the two. [Drafter-only load bracket](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/patch_dflash_w4.py#L1-L41), [target activation](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/radiance_verifyhead.py#L111-L139)

4. **Default compressed all-reduce changes target arithmetic too.** Image defaults enable `RADIANCE_USE_R4D_AR=1` and `RADIANCE_USE_R4D_AR_QUANT=1`. Current source selects a lossy Walsh-Hadamard rotated six-bit all-reduce for compatible messages of at least 128 KiB, using an exact path for smaller messages. This is not merely lower draft precision. It can affect target prefill and sufficiently wide speculative verification batches. For illustration, eight requests with seven draft positions plus the next-token row at hidden size 5,120 form 640 KiB of BF16 hidden states; actual activation additionally depends on tensor layout/group alignment and runtime configuration. No runtime log here proves whether a particular uploaded run took this path. Older docs mentioning FP8 payloads should not be substituted for this version's six-bit source. [Kernel identity/defaults](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/radiance_allreduce.py#L8-L37), [lossy kernel selection](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/radiance_allreduce.py#L117-L150), [message gate and dispatch](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/radiance_allreduce.py#L189-L229)

5. **Exact 1.0.16 source still explicitly leaves DFlash unqualified for strict cross-mode identity.** Its README says the strict speculative/non-speculative greedy gate has not passed, although meaningful-output and sampled tool-call checks passed. Historical reports preserved at this commit contain quantitative failures, but those are older campaigns, not fresh 1.0.16 measurements: the 0.9.3 continuation reports 2/8 matches for ordinary K5/K7 and fast K5, 1/8 for fast K7, and 2/8 for fast MTP. Another older FP8 investigation records sensitivity to verification shapes and payload precision. Do not label the old 2/8 result as the measured 1.0.16 outcome. [Version-pinned current qualification statement](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/README.md#L266-L276), [historical 0.9.3 results](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/docs/RADIANCE_093_R4D050_MXFP4.md#L168-L188), [historical FP8 controls](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/docs/DFLASH2_OPTIMIZATION.md#L66-L90)

6. **Adaptive verify width does not inherently skip verification of emitted draft tokens.** The scheduler removes unused proposals before scheduling and observes acceptance to choose subsequent widths; it does not simply emit unverified tail tokens. Width changes can still change numerical paths, so the source's general algorithmic losslessness language is not proof of token identity for this implementation. [Scheduler cap implementation](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/patch_dynwidth.py#L1-L22), [actual truncation](https://github.com/magiccodingman/vllm-radiance/blob/f295b9ef51ad413a68e4192371e0377741a354ce/patch_dynwidth.py#L82-L99)

## Implication for our official FP8 model

There is a plausible DFlash research direction, but this source does not justify promoting the complete Radiance speed configuration as lossless. A bounded future candidate should retain the official target, its existing KV/arithmetic contract, a faithful full-vocabulary target head, and exact target collectives; isolate the draft change and first require complete-token identity versus our qualified reference. Draft W4/INT2 should be separately gated after a working matched drafter is available. Disabling these shortcuts alone is not sufficient proof because the preserved historical controls also found verification-shape drift. No current B70 compatibility, speed gain, or quality result is established by this audit.
