## Experiments worth screening

1. **Qwen3.8-27B Q8_0, single-token llama.cpp decode.** The change adds a four-block stripe to an existing ESIMD matrix-vector kernel. It reads a tail of 32 blocks in one pass with eight workers. The contributor reports 17.3 to 14.9 µs for an Inkling output projection and 64.0 to 64.5 tok/s for generation. The lab’s Qwen GGUF header contains 370 two-dimensional Q8_0 tensors of width 5,120 and 64 of width 17,408. Both widths leave exactly 32 blocks after the existing 64-block passes. The other 64 tensors of width 6,144 leave none. The eligible widths include the 64 feed-forward gate, up and down projections each. These are shape counts only. Confirm the reordered ESIMD kernel actually handles these projections in the intended runtime, measure those shapes, and compare exact outputs. The change redistributes the tail across workers, so the sum can round differently. A single-card decode A/B on the same model and prompt follows if the screen passes. [Contributor’s delta and timings](https://github.com/ljedrz/llama.cpp/commit/c17ae566f16d2f4d2d29bb06a5ad037d66096f9a)

2. **Inkling, reading new tokens deep into a prompt.** The fork divides a long key range among more GPU workers and combines partial attention results. On the contributor’s B70, splitting took a 1,024-token append at 131,072 depth from 1,220 to 1,323 tok/s. The same commit reports little change in shallow prompts. First isolate scheduling on the pinned fork with the same GGUF, F16 K/V, prompt IDs and 1,024-token batch, comparing `GGML_SYCL_FA_XMX_SPLIT=1` with automatic splitting in separate processes. Capture logits, kernel time, end-to-end append time and energy at 32K and 128K. For the native runtime, the candidate is parallel computation of the existing 128-key block contributions with the same FP32 arithmetic and final fold in ascending block order. Include scratch traffic and fold time in the comparison. The native prompt kernel already applies position bias in place. The fork rounds scaled queries and softmax weights to FP16, then merges split-local softmax states using a different order. The lab also measured a previous three-part XMX score variant at 46.1 ms against 41.1 ms for FP32 at 512 rows by 100K keys. A direct transplant has no established bit-exact result. ## Other leads

- The fork reads two 648-byte NVFP4 expert rows as one 1,296-byte row to satisfy the 2D block-load pitch requirement. This is a concrete llama.cpp optimization for weights in their stored layout. The native runtime already repacks NVFP4 for its own exact XMX expert kernels. Its current layout has a different load path. [Paired-row patch](https://github.com/ljedrz/llama.cpp/commit/31adc5c30790b0d626405a82a03dbbf6aba41db9) · [Lab layout](../../experiments/own-xpu-runtime/inkling2/src/xmx_moe.hpp)
- For llama.cpp workloads using separate F16 KV matrix-vector operations, reusing one query across several KV rows is a possible secondary screen. The contributor’s deep-context decode numbers used flash attention disabled. The lab Nemotron recipe uses a 30B-A3B UD-Q4_K_M model, while the issue’s 35.0 to 53.2 tok/s is a bundle result for a different 74B MoE with mixed tensor formats. [KV patch and flags](https://github.com/ljedrz/llama.cpp/commit/f5c80a4722afc90c0d04c080682270119a71ad0b) · [Lab Nemotron recipe](../../repro/nemotron-35-lightning-30b-a3b-b70/README.md)
- The issue’s one-B70 243K result (182 s with DSpark loaded) used UD-Q4_K_XL. The native lane uses UD-IQ4_XS. The idle-power observation concerns sensor polling during idle transitions. Neither item establishes a change to the lab’s measured throughput or active-load energy.
