# Lumnus v0.30.0 stack: source review for Flash-Next FP8

Date: 2026-10-08 UTC (2026-10-07 evening in Toronto). Scope: CPU-only source analysis on `steve-b70s`; no runtime qualification. The external performance evidence remains **community-reported**. This note is an analysis, not a runnable contributed recipe or a promotion. The requested host restrictions take precedence over historical launch/build instructions.

The new stack is worth a bounded exactness-first port, but it does not establish a faster lossless FP8 lane. Most of its infrastructure patches are not W4A16-specific. Its standard sampler target-verifies drafts, while its fused GDN arithmetic is not the lab's certified serial arithmetic. Its PLE compression and response defaults must not enter the unchanged-weight experiment. The existing **46.854250 tok/s** result and both exact pins remain unchanged. Sources: `B/README.md:77–95,132–141`; `B/engines/common.env:26–37`; `K/csrc/xpu/gdn_attn/gated_delta_rule.hpp:392–525`; `R/results/qwen38-flash-next-fp8-b70/CLOSEOUT-20260913.md:5–12`; `R/repro/qwen38-flash-next-fp8-tp4-mtp1-exactgdn-b70-47tps-20260913/identity.json:101–114`.

## 2. MTP, target verification and the exact-output boundary

### What their MTP3 actually does

- The example server explicitly sets `{"method":"mtp","num_speculative_tokens":3}`, `--no-async-scheduling`, BF16 compute, TP4/EP, and full plus piecewise graphs. Capture sizes include four-row multiples through 64. Its default temperature is 0.7, not the lab's deterministic authority request contract. [B/engines/serve-s16-mtp3.args:4-21]
- Config maps Qwen4Exp to `Qwen4ExpMTP`, extracts the checkpoint MTP layer count and HC multiplier. XPU falls through to the `nvidia` package (the directory name does not imply CUDA-only execution). [V/vllm/config/speculative.py:832-851; V/vllm/models/qwen4_exp/__init__.py:22-48]
- The MTP module loads checkpoint `mtp.*` tensors, has token embedding and previous-hidden projections, uses full-attention decoder layers, and selects its layer as `spec_step_idx % num_mtp_layers`. The next speculative step receives multi-stream hidden state. Thus three speculative tokens are successive proposals through the MTP machinery, not three independent targets or three free accepted tokens. [V/vllm/models/qwen4_exp/nvidia/mtp.py:91-118,179-219,280-341]
- In the V1/common proposer, the first draft is followed by `range(num_speculative_tokens - 1)` subsequent forwards, feeding the preceding draft token and hidden state, advancing positions, rebuilding attention metadata, and sampling again. For K=1 it returns after the first proposal. [V/vllm/v1/spec_decode/llm_base_proposer.py:618-640,687-769]
- The served V2 path uses `MTPSpeculator(AutoRegressiveSpeculator)`: the step count comes from static config, first proposal feeds subsequent forwards, and `range(1, self.num_speculative_steps)` generates later tokens. This is the active-path counterpart of the common proposer above. [V/vllm/v1/worker/gpu/spec_decode/mtp/speculator.py:12; V/vllm/v1/worker/gpu/spec_decode/speculator.py:108; V/vllm/v1/worker/gpu/spec_decode/autoregressive/speculator.py:647–665]
- Target XPU GDN goes through input projection -> `gdn_attention_core_xpu` -> gated norm/output path. The wrapper dispatches `_xpu_C.gdn_attention`, or optional external `_gdn_index64.gdn_attention` if present/mode-selected. The modern stock operation uses `causal_conv1d_spec` followed by `gated_delta_rule_spec`; it also handles nonspec rows in the same call. [V/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:976-1020; V/vllm/_xpu_ops.py:154-178,222-303; K/csrc/xpu/gdn_attn/gdn_attn_interface.cpp:767-861]
- The speculative recurrence initializes from `cache_indices[request, accepted_count-1]`, processes the compact query-start interval, writes an output for each verifier row, and writes each row's recurrent state into a separate rollback column. Accepted-count metadata chooses the correct state next iteration. Three drafts normally mean four target verifier rows (three draft decisions plus bonus). [K/csrc/xpu/gdn_attn/gated_delta_rule.hpp:280-291,392-416,496-525; V/vllm/v1/sample/rejection_sampler.py:747-772]

### Token acceptance is strict; target arithmetic equivalence is not established

The default is `rejection_sample_method="standard"`. Greedy standard mode computes target argmax and accepts a draft only when its token ID is equal; it writes target argmax at the first mismatch and stops accepting further drafts. If every draft matches, it appends the separately sampled target bonus. There is no epsilon, logit-gap allowance, or approximate token-match in this checked path. [V/vllm/config/speculative.py:517-523; V/vllm/v1/sample/rejection_sampler.py:466-481,747-772]

The served V2 sampler independently has the same standard greedy equality rule (`accepted = target_argmax == draft_sampled`), while non-greedy standard verification uses the log probability ratio. Therefore the conclusion is not dependent on the V1 implementation. [V/vllm/v1/worker/gpu/spec_decode/rejection_sampler_utils.py:571–594,657–665]

In the V1 reference path, non-greedy requests use target probabilities, draft probabilities (or 1 if draft probabilities are absent), `target_prob / draft_prob >= uniform_prob`, and recovered-token sampling on rejection. This is standard distribution-preserving rejection machinery, not a promise of the same sampled string for the same seed. [V/vllm/v1/sample/rejection_sampler.py:483-498,852-885]

There IS an upstream synthetic benchmark acceptance mode: it can accept a draft based on a configured synthetic rate independently of target token equality. It is opt-in, the inspected Lumnus serve args do not enable it, and it must remain off in the lab lane. This is not a tolerance found in their published standard verifier. [V/vllm/config/speculative.py:517-536; V/vllm/v1/sample/rejection_sampler.py:84-97,752-761; B/engines/serve-s16-mtp3.args:20]

Crucially, strict rejection only verifies against the logits this new target implementation computed. The new spec GDN carries `state_local` in float across verifier rows, writes `static_cast<StateT>` snapshots, but does not cast the carried float state back through `StateT` between rows. Separate single-token calls do reload their cache-rounded state. The certified identity explicitly requires BF16 cache passage between rows (`R/repro/qwen38-flash-next-fp8-tp4-mtp1-exactgdn-b70-47tps-20260913/identity.json:99`). If `StateT` is BF16 this creates an explicit potential arithmetic difference; if `StateT` is float32 that particular rounding difference disappears, but old/new fusion/reduction/compiler equivalence still is not proved. Do not turn this source-level risk into an observed FP8 token mismatch: no such execution was performed. [K/csrc/xpu/gdn_attn/gated_delta_rule.hpp:392-416,457-488,507-525 versus non-spec :136-145,238-247]

The lab exact mode instead invokes the existing single-row decode arithmetic row by row inside one extension operation, including cache state transfer/rounding. It was generalized from four verifier rows to any positive row count for a single request and requires persistent scratch plus an in-order queue. The promoted settings are `VLLM_XPU_GDN_SERIAL_SPEC_DECODE=0`, `VLLM_XPU_GDN_NATIVE_SPEC_RECURRENT_SERIAL_EXACT=1`, `VLLM_XPU_GDN_SPEC_PERSISTENT_SCRATCH=1`, `VLLM_XPU_GDN_NATIVE_SPEC_COMPLETION_BARRIER=1`. ### Metadata fusion is distinct from recurrence fusion

Patch 0004 (`a69839d3450fc16477c15c9bab4140ad71952ff1`) fuses integer ALIGN gathers and metadata staging across the 36 GDN builders; it does not implement a tolerant verifier or change recurrence equations. ### A387: does this answer the negative MTP2 result?

A387 already used native extension exact serial GDN with three verifier rows. It retained both current authority hashes at 2K/4K, but ran ~43.9/~44.5 tok/s vs ~48.2/~48.5 for MTP1. The recorded reason is that the third target row cost more than the extra accepted draft returned; short high-acceptance rows did gain ~6%. It was not merely the earlier Python serial dispatch tax. [R/experiments/qwen38-flash-next-fp8-b70/notes/2026-09-13-a387-mtp2-exact-mode-screen-result.md:3-13,23-31]

Inference: metadata fusion may reduce per-step overhead, and faster new MoE/GDN implementations may shift the break-even point; these are reasonable candidates. But no inspected result isolates FP8 MTP1 vs MTP3 with certified exact target arithmetic, and serializing the new recurrence to preserve arithmetic can surrender part of its speed. Therefore their approach does NOT yet demonstrably solve A387. Their published acceptance length and AWQ speed do not establish a result for this lane. ### GDN and exact-output implications

- New upstream kernel work since the common base includes `1d5b4f5e5ddd8da96ea23c76d7e7421b00083fdb` (fix mixed speculative/non-speculative token groups after GDN split) and `5802a414d47855b01b63121bce3655795ef8dfa8` (token-indexed convolution rollback layout and strided-cache state length). - The new convolution layout keeps one cache line at cache_indices column0 with `(width-1)+num_spec` rows, reads accepted window beginning at `num_accepted_tokens-1`, and rolls history plus draft inputs within that line.
