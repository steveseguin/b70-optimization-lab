## Purpose and preservation boundary

measured a 9.372254 tok/s median. The official vLLM Flash-Next recipe recommends
three speculative tokens and says TP4/TEP4 with MTP3 is validated on its NVIDIA
reference platform. This arm fills the corresponding B70 matrix cell without
changing the accepted target, host placement, cache, or MTP0/MTP1 recipes.

MTP3 reuses the checkpoint's one trained MTP layer sequentially; it does not
add another model-weight set. The only server-axis change from accepted MTP1
attempt 3 is `num_speculative_tokens=3` and the additive campaign/cache path.
The client retains `chat_template_kwargs.enable_thinking=false`.

## Attempt-1 command-identity closeout and attempt 2

Attempt 1 passed the static engine preflight for MTP3 and loaded all 131 target
checkpoint shards on all four ranks. Before health, quality, or timing, an
independent comparison of `identity.txt`, the recorded server command, and the
load-memory profile found that the final server command did not contain
`--speculative-config`. The common launcher had generalized its validation and
static engine construction to MTP0-4, but its final argument builder still
appended that option only for MTP1. The process was therefore an MTP0 load under
an MTP3-labeled directory. It was stopped immediately. Attempt 1 has no model
response, quality result, speed row, or valid MTP3 evidence and must never be
resumed or relabeled.

Attempt 2 corrects only command construction. One canonical JSON value is now
created from `MTP`, used by the static engine preflight and final server
argument builder, and checked immediately before launch. MTP1-4 must have
exactly one matching `--speculative-config`; MTP0 must have none. The model,
runtime, TP/EP, placement, cache, quality, and timing gates above remain
unchanged. The wrapper now requires `ATTEMPT=2`; attempt 1 remains preserved as
infrastructure-only evidence.

## Attempt-2 prelaunch closeout, recovery, and attempt 3

Attempt 2 never constructed or launched a server. Its bounded initial
four-card discovery timed out with an empty output file. Passive journal review
then showed delayed device work from the interrupted attempt-1 load timing out
after the model processes were already gone. Attempt 2 therefore has no model
load, server command, response, quality row, speed row, or MTP evidence.

After a quiet window, passive ownership checks proved no process held any of
the four render nodes, the display manager was inactive, the console remained
on AST, and the booted command line retained `xe.disable_display=1`. The
documented four-card xe reload completed without reboot. A single post-recovery
gate then passed:

- exact discovery of all four B70 identities;
- allocation/copy/compute with the exact expected sum on every card;
- one four-device peer-read oracle;
- one four-rank XCCL barrier/all-reduce with exact `4.0` on every rank;
- a clean post-recovery journal scan and no residual device holders.

Raw recovery evidence is under
`/mnt/usb-models/bench-results/qwen38-flash-next-fp8-b70/recovery-after-mtp3-attempt2-20260827T1120`.
Attempt 3 uses the corrected committed command builder and fresh run/cache
roots. Its first complete response is also the required post-recovery model
generation canary; no quality or timing can run before that succeeds.

## Attempt-3 cache-admission closeout and attempt 4

Attempt 3 passed the restored hardware/XCCL preflight, recorded exactly one
MTP3 speculative configuration in the real server command, loaded the complete
target and MTP weight sets on all four ranks, and reached cache admission. It
then failed closed before warmup or any model response because the inherited
192-MiB MTP1 cache was too small for one MTP3 request. All workers exited
normally, no process or listener remained, and the launch-local journal delta
was clean. Attempt 3 has no generation, quality, or speed evidence.

An exact current-source cache construction found a shared-pool block size of
11,767,808 bytes. MTP3 at maximum length 512 requires 18 usable blocks plus one
reserved null/admission block. The hard floor is therefore 223,588,352 bytes;
attempt 4 uses 20 exact blocks, 235,356,160 bytes (224.453125 MiB), leaving one
spare block. This is the only runtime-axis change from attempt 3. The common
launcher's default stays 201,326,592 bytes, preserving every MTP0/MTP1 launch
identity and captured result.

For the later deployment-shaped maximum 4,352 (4,096 active prompt tokens plus
256 output tokens), the independently calculated conservative MTP3 value is
25 blocks or 294,195,200 bytes. That deeper-context identity is not folded into
attempt 4 and requires its own preregistration and qualification.
