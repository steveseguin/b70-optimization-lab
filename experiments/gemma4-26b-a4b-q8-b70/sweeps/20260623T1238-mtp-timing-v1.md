## Hypothesis

The current `91.16 tok/s` Q8 draft-MTP record may be limited by the Gemma MTP
hidden-state handoff: target `h_nextn` is copied device -> host, kept in CPU
buffers, then uploaded back into the draft MTP graph as `batch.embd`. If that
round trip is expensive, a device-resident handoff would be the next source
patch to attempt.

## Patch

Diagnostic-only source patch:

- `patches/gemma4-llamacpp-mtp-timing-v1-20260623.patch`

The patch adds `LLAMA_MTP_TIMING=1` counters in `common/speculative.cpp` for:

- common speculative `process()` time, previously invisible;
- MTP process scan / hidden row fetch / CPU copy;
- MTP draft init / `llama_decode(ctx_dft)` / sampler / hidden fetch / batch
  build;
- MTP accept pending-state copy.

The patch does not change draft choices, target verification, sampler settings,
or hidden-state copies. It only records timings when `LLAMA_MTP_TIMING=1`.

## Decision

Diagnostic win, performance-patch rejection.

The hidden-state CPU round trip is **not** the current bottleneck. Across the
full timing run, target process hidden fetch + copies were only about `3.6 ms`,
draft batch building was under `0.5 ms`, and accept copies were about `0.1 ms`.
Even removing them entirely would not materially move a `~5.6 s` / request
decode.

The expensive MTP-side buckets are:

- draft `llama_decode(ctx_dft)`: `1693 ms`;
- sampler/candidate work: `275 ms`.

The rest of the wall time is target verification / graph execution. Future
source work should not start with a device-resident hidden handoff. Better next
targets are reducing draft decode cost, reducing sampler overhead without
changing quality, or improving target verifier throughput / batching.

Do not submit this run to LocalMaxxing: reduced `16/16` canary, diagnostic
source patch, and below the current `91.156717 tok/s` record.
