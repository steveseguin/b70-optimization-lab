# 2026-06-23T2249 - Lazy MTP verifier hidden-row copy

Goal: test whether the current Gemma 4 26B A4B Q8 draft-MTP record is limited
by host copies of target `h_nextn` verifier rows in `common/speculative.cpp`.

## Patch

Patch snapshot:

- `patches/gemma4-llamacpp-mtp-lazy-verify-h-20260623.patch`
- sha256:
  `78173f5d302d4548f7842d2284347fb252878b2834081cb37ff9ec14a02b36ee`

The patch added `LLAMA_MTP_LAZY_VERIFY_H=1`. In the Gemma shared-memory MTP path
it skipped copying every target verifier hidden row into `verify_h`, copied only
the last row into `pending_h`, and lazily fetched the selected row at `accept()`
for partial accepts.

## Result

All runs below used the current fresh-response record stack plus
`LLAMA_MTP_LAZY_VERIFY_H=1`, `CANARY_REPEATS=16`, `BENCH_REPEATS=4`,
`BENCH_PROMPT_MODE=filled-long`, and `cached_tokens=0` in every benchmark row.
They are smokes, not promotion runs.

Current record to beat: `92.39728860909672 tok/s` on the first measured request
after TTFT, from `gemma4-q8-gpu0-mtp-n7-c926-fastargmax-cpucleanup-vmm0-ub512-poll100-full-ctxcp0-nmin2-pmin012-nobs-dthreads32-dtb32-filled-long-20260623T222838Z`.

Profile comparison shows why this lost: verifier-row host copies are not a
meaningful bottleneck. In the promoted fast-argmax full run, profile totals near
the end were roughly:

- `process_ms=35.801` over `29936` verifier rows;
- `accept_copy_ms=0.467`;
- `draft_decode_ms=12622.961`;
- `fast_scan_ms=801.684`.

So the expensive parts are draft decode and vocab scan, not the verifier hidden
row copies. The lazy patch was reverted from the active llama.cpp source tree
after these smokes. Keep the patch snapshot as a negative result so this path is
not rediscovered.
