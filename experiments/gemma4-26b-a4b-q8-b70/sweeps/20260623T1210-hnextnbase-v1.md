# Gemma 4 Q8 MTP h_nextn base-pointer patch v1

Date: 2026-06-23
Owner/agent: Codex

## Hypothesis

The Gemma 4 MTP target hidden-state handoff copies `h_nextn` rows from the
target context into CPU `verify_h` / `pending_h` buffers. The baseline loop calls
`llama_get_embeddings_nextn_ith(ctx_tgt, row)` once per row; each public getter
synchronizes and runs `output_reorder()` before returning. Since the target
context enables `embeddings_nextn` in unmasked mode, rows are already dense by
raw batch index. Replacing the per-row getter calls with one
`llama_get_embeddings_nextn(ctx_tgt)` call plus a contiguous `memcpy` should be
semantics-preserving and might reduce handoff overhead.

Patch artifact:
[gemma4-llamacpp-mtp-hnextnbase-v1-20260623.patch](../../../patches/gemma4-llamacpp-mtp-hnextnbase-v1-20260623.patch)

## Decision

The patch is correctness-safe under the full gate, but it is not a performance
win. Best result was `90.213100 tok/s`, below the current record
(`91.156717`) and below the unpatched four-repeat best (`90.314502`). Do not
promote or submit to LocalMaxxing.

This rules out repeated target-side `llama_get_embeddings_nextn_ith()` calls as
the dominant cost. The remaining high-leverage path is deeper instrumentation
or device-resident hidden-state handoff / draft-input upload work, especially
around draft `llama_decode(ctx_dft, batch)` and host-to-device hidden input
copies.
