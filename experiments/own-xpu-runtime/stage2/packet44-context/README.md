# Packet 44: real allocation capacities

CPU preparation in progress. No device ran and no speed is claimed.

This is a copy of packet38-integrated, with target arithmetic
`iq3-p17-detmath-v2`, the same dispatch names, two ranks, native controller and
official draft head. It admits 256, 4096 and 32768 positions. Full BF16 caches
remain in place. The exact copied source identities are in baseline.json.

Capacity reserves storage. It does not increase the number of keys scored or
values reduced for the same short request. Selection and attention use an
independent launch bound rounded to 32 positions, then actual valid/selected
counts for arithmetic. Only affected prepared commands are refreshed when
that bound changes; each recurrent bank and the draft track their own bound.
Pooling launches only append work and newly completed groups. Request reset
and allocation still cost more at a larger capacity; they are outside token
kernel execution. Device wall time, including re-preparation, remains unmeasured.

CAPACITY.md inventories all ten capacity-sensitive components. KERNELS.md
records the finite timing grids and the launch-floor rationale. Selection keeps
the arithmetic-v2 stable descending-score order, lower block ID on ties, four
positions per complete block, then the trailing partial block. This is the lab's
fixed deterministic arithmetic order; the official model supplies the structural
selection rule and does not promise that same tie/output order.

The per-card allocation plan is memory-plan.json, generated by memory_plan.py.
Historical packet38 allocation censuses verify both exact baselines. The plan
retains their compressed, hash-bound bytes so it can be checked from a clean
clone. All numbers below include target caches, the draft on rank1, scratch,
rollback storage and the larger RoPE table.

| Capacity | Rank0 modeled bytes | Rank1 modeled bytes | Rank0 admission ceiling | Rank1 admission ceiling |
| ---: | ---: | ---: | ---: | ---: |
| 256 | 27,257,169,468 | 31,203,510,986 | 27,303,670,016 | 31,204,739,786 |
| 4,096 | 27,311,728,188 | 31,267,162,826 | 27,358,228,736 | 31,268,391,626 |
| 32,768 | 27,719,099,964 | 31,742,429,898 | 27,765,600,512 | 31,743,658,698 |

The ceilings add explicit reserves of 46,500,548 / 1,228,800 bytes for ranks
0/1. Against a 34,242,297,856-byte card, rank1 retains 2,973,906,230 bytes at
4,096 and 2,498,639,158 bytes at 32,768 after reserve. Both clear the 1.5 GB
floor. No layer move or reduced cache precision is necessary. Each window
checks its actual owner census before requests. Driver overhead and physical
residency still require the coordinator windows.

Only this directory is writable. Build output is ignored; CPU preparation keeps
it below 4 GB and reserves 8 GB root free space. Coordinator wrappers have the
requested 6 GB packet limit. Fixture scratch is hashed, compressed and removed
after each gate. The 4 MiB rope.bf16 constant is intentionally retained: its
first 524,288 bytes equal packet38 exactly, and generate_rope.py reproduces the
extended table with a pinned receipt. The table defines arithmetic, not a cache.
[LARGE-ARTIFACTS.md](LARGE-ARTIFACTS.md) records retention and restoration details
for the table and the large gate ledgers.

WINDOW.md contains coordinator commands. INTEGRATE.md lists deltas against the
copied base for the independent packet40 work. build-receipt.json will mark
qualification complete only after the actual CPU gates and compiled artifacts
are verified. Historical packet38 receipts are not reused as packet44 passes.
