# Packet65 CPU preparation — closeout

<!-- campaign-closeout -->

## Question and identity

Can the packet64 routed-expert class run at least 30% faster in its real layer
composition while preserving the packet49 oracle? October17 CPU preparation,
Qwen Flash-Next quantized compressed IQ3 lane, unchanged packet64 weights,
24/24 target split on two B70s, rank1 production draft and ordinary rollback
copies. The selected arithmetic is `iq3-p49-split32-v1` with full BF16 KV.

## Outcome

CPU preparation passes. There is **no measured device performance result**.
Production plus four selectable candidates share the sealed new binary.
The coordinator must establish exact device output and the class reduction
in two fresh matched pairs. A class screen alone is not integration or record
qualification.

## What worked

- Actual kernel host paths match production in72 cases per process, with
  110,592 raw FP32 chain and3,456 tree checks. GNU and Intel each pass two fresh
  processes; all output bytes match, including exceptional inputs and errors.
- Complete host engine target fixtures match packet64 under all five choices
  and the new attribution mode. The actual native parser passes14 cases.
- Offline compilation of all ten production/candidate kernels shows128
  configured GRFs and no spill or scratch messages. Wide raw loads reduce
  static load and instruction counts; no speed is inferred.
- In-composition timing follows complete real target layers and packet57’s
  full class. The gate checks packet49 output tokens directly, recorded output
  hashes, matching setup and two independent AB/BA pairs. Whole-host admission
  cooperates with the existing chain and blocks legacy lane screens.

## What failed or remains uncertain

The original one-tile-lookahead hypothesis survives as earlier raw loads, but
compiler waits precede current decode. Its larger static instruction body
could regress. WG scheduling improvements are also unmeasured. Residency,
actual outstanding requests and installed-driver JIT behavior remain unknown.

During CPU preparation, the first build refused missing copied prototype/RoPE
inputs; they were supplied without changing arithmetic. The first mini-engine
harness omitted its local metrics helper; the helper was copied and all final
runs passed. A later helper invocation correctly refused absent
`OMP_NUM_THREADS=2`. No GPU or model server was involved in any refusal.

Independent review strengthened attribution evidence binding before any device
run: consumed files now must match completion-time hashes. Earlier CPU seals
are retained only as superseded preparation history; final seals alone apply.
