## Question and identity

Can fewer rank-1 MTP head bytes improve the packet75 record configuration
without changing target outputs? The baseline is the Unsloth Flash-Next
UD-IQ3_XXS quantized model, packet75 source bundle, packet49 target oracle,
24/24 layers, rank-1 draft, 4096 context and BF16 KV. Preparation was CPU-only
on steve-b70s, October17,2026. No model server or GPU program ran.

## Outcome

Four views are sealed for diagnostic screens: production, Q4/g32 at91,392rows,
prefix80,128, prefix74,752. Both complete lane grids and every possible other-lane
confirmation plan pass. Four proposed queue lines pass in a temporary directory;
no live queue was edited. Actual device exactness, acceptance, speed and fresh-device
repeat evidence are pending. No candidate is promoted.

The Q4 bandwidth projection is260.389us,1.617% of the stated16.1ms hit cycle,
before acceptance changes. Prefix projections are64.186us and94.820us. These
are not measurements. The raw packet77 census separates201.812us of unattributed
wall time; it cannot identify pure fixed launch overhead.

## What worked

- Target source bodies remain packet75. Only `mtp.hpp` and the draft selection
  registry differ among copied runtime files; inherited objects are hash-checked.
  Fresh miniature target tokens and96 retained layer fixtures match packet75
  for every view. Both fresh draft transcripts and final states agree per view.
- Both GNU and Intel process all91,392 actual Q6_K prefix rows twice, produce
  identical derived Q4 bytes, and match a separate reference for every full-width
  head output. This covers the real2560-column path, not only the16-column mini.
- Eight full-shape startups reach allocation, post-load preparation and the selected
  head kernel with payload-only mocks. Both target and Q4 undersized allocations
  refuse, as do four invalid draft selections. The actual memory gate passes.
- Q4 rank1 owns31,413,390,026 device bytes and4,214,796 pinned bytes. The added
  head is146,227,200bytes; arena headroom798,864,694bytes. The reserve-inclusive
  ledger leaves2,827,679,030bytes free; no memory limit was lowered.
- Eighty shared-wrapper checks and nine packet checks pass. Four seals bind
  the actual shared v4 wrapper. Both lanes have full grids and winner-gated
  confirmations. Acceptance is recomputed from hit/guess counters per request.

## What failed or remains uncertain

The initial CPU runner correctly refused reused output paths after the report-only
rebuild. It now creates a fresh attempt directory and retains earlier miniature
artifacts. The first Q4 negative check expected a kernel extent message; the
real guard rejected the shortened allocation sooner, at upload. The assertion
was corrected without weakening the refusal requirement. The first real-header
check included alignment padding; it now parses the header and verifies exactly
the authenticated header bytes before any prefix payload read.

GPU reduction behavior, model-output equality, acceptance and throughput remain
unmeasured for these candidates. Coverage is a text-frequency proxy, not an
acceptance forecast. CPU synthetic activations exercise every real head row but
do not model target-generated activation distribution. Shared-screen quality
checks remain mandatory. The final512-token promotion gate is not satisfied.

The normal50GiB disk reserve check failed at about19GiB available; preparation
used the brief's explicitly bounded below1GB build budget and removed no other
work. Build logical size at final check is160,444,769bytes. Compiler peak child
RSS was731,772KiB under the8GiB process limit; compilation was serial.
