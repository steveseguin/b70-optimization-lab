# Packet91 CPU preparation — closeout

## Question and identity

Can packet84's chained selection add route-fast, optionally with packet82b's
rec-both-plus, without changing target arithmetic or interfering with the running
chain? This is the quantized compressed Unsloth UD-IQ3_XXS lane, unchanged
`iq3-p49-split32-v1` arithmetic and packet49 oracle, two B70 cards per screen.
Preparation is CPU-only on October 18; no device speed is measured here.

## Outcome

The copied bundle supports four independently sealed compositions. Packet84's
binary supplies control and route-fast. Packet82b's already-built binary supplies
the two rec-both-plus compositions. Both are reused by exact hash. Device output,
acceptance, matched speed and a fresh record chain remain pending.

## What worked

Fresh complete-state recurrence byte checks pass under GNU and Intel twice each.
The independent route operator proof is hash-bound from packet84. Every view
passes both ranks' real post-load startup/capture/allocation path with backend
and payload mocks. The submission collector replays bound admission bytes;
placement-aware draft notes stay under 2,000 characters. The packet90 expert/HC
slot is empty and refuses unqualified additions.

## What failed or remains uncertain

Review caught external binary symlinks incompatible with the shared v4 safe-path
rule and repeat seal creation incompatible with immutable view seals. Local hard
links and verify/reuse fixed those paths before device use. Broader tests exposed
stale inherited test defaults and an assertion assuming every temporary test
root lived outside the repository; those tests now cover the registered baseline
and both path forms. Generating a queue seal after a chain seal correctly
invalidated the old chain seal; the final sequence seals queues first.

None of this establishes a speedup. Historical p78/p84s timing is a lead only.
New screens must be 13/13 exact and the same complete candidate must beat both
same-lane controls on both lanes. No independent winners are stacked silently.
