# Screen v3 CPU preparation — closeout

<!-- campaign-closeout -->

## Question and identity

Can an independent two-card screen accept the same lean and selected TP2
lineages as v1 while retaining v2's lane scheduling and safety gates?
October 17, 2026; `steve-b70s`; packet49 arithmetic and exact token oracle,
context 4096, BF16 KV, native target split 23/25, draft rank 1.

## Outcome

CPU preparation passes. All 26 tests pass, including a complete fake-transport
v1/v3 byte comparison and both token/attribution orchestration. Six candidate
plans (three lineages, both lanes) and one crossover plan pass. No native
program, GPU window, model load or service ran. Native device isolation,
full-model exactness and speed remain unmeasured in v3.

## What worked

The controller belongs to the wrapper seal, so lean candidates no longer need
controller source files. The fixed BDF prefilter admits exactly the intended
PCI pair on this host. Local native indices become 0 and 1 for both lanes.
Fixture fdinfo checks reject wrong/missing PCI devices, unreadable own-rank
records and PID reuse, and invalidate a prior pass when a foreign FD appears.
The teardown gate tests preserve at least 60 seconds between complete drains.
The current passive journal capture has exactly two known fault records.

## What failed or remains uncertain

Standard selectors alone do not provide a pre-open DRM filter in the inspected
Intel driver. V3 therefore uses its `FilterBdfPath` before ordinary selectors.
This choice is supported by source inspection and passive topology checks;
only the coordinator's native fdinfo evidence can establish its behavior on a
real launch. There is no speed verdict from CPU fixtures. Unreadable foreign
clients still require coordinator ownership review. Old unmasked workers
holding both pairs still prevent admission. No old result is reclassified.
