Dedicated fixed depth2 versus depth3: configuration-only material screen
Source audit2026-10-28; no GPU, compilation, planner execution or model/tensor reads.

Decision
Worth one controlled screen after the active all-owner reset gate qualifies.
Use existing fixed capacity/depth2 instead of depth3, same reset-capable binary,
3targets+dedicated draft and cuts0/17/33/48. No new requested-depth protocol,
engine/wire change, adaptive policy or training is necessary for this question.
This is a different, cheaper question than backlog8's capacity3/request1 gap.
It changes BOTH ring capacity and requested native proposal depth; do not call
it depth2 requests inside capacity3 or claim isolated head-compute savings.
No speed/correctness result is claimed here. Backlog left unchanged.

Actual supported selectors and constraints
engine/tools/dedicated_provider_driver.py42–43 accepts config speculative_depth
as exact int in(2,3), default3. It stamps depth into request identity and emits
--pipeline-ring-depth on provider and target argv (around97/119). Two or three
target stages are accepted; provider must be a different physical card.
Current native main.cpp421/438 accepts2/3; depth3 requires persistent ring
provider mode439. Both geometries exist in one binary, not separate builds.
Current ring_live_wire.py39–42/86–109 accepts2/3, proposal metadata192B for2,
224B for3, and validates matching capacity/available guesses/reserved words.
Provider runtime.hpp56 requires request.depth==context.depth for BATCH,0 for
non-head/control. Owner constructs fixed Sequence(context.depth). Changing the
whole fixed context to2 already meets this contract. Truncating Python guesses
while retaining context3 would still execute3 native heads and is not this arm.

Why this before another large integration
The completed512 expert operator screen passed64gates but weighted gains
7.892480%cold/7.893969%hot missed its>10% integration threshold; that lever is
closed. Fixed depth2 uses existing machinery and could reduce real proposal/
rejected work, with no new wire/continuation surface. It is worth measuring,
not claiming a gain from the old bound. Closed head-row sharding need not be
reopened for this configuration-only question. No assumption is made that old
2+1 timing transfers to3+1; current route/acceptance/lifecycle evidence decides.

Minimal preregistration using existing harnesses
1. Wait for root's active all-owner reset qualification, retaining its exact
binary/build receipt and Python pins. Current ABA64K config is3+1 cuts17/33,
context65536,depth3,prefill256,4slots,capture-ready+bulk stage pipeline,
reference target tie-sort, measured check policy and unchanged BF16 draft.
Choose that same geometry for both depth arms; do not simultaneously change
cuts to equal16, context, lookup placement, rows, slots or reference routing.
Use fresh exclusive paths; read actual planner floors/payload bounds. Preserve
normal root monitor/fault-halt rules. No host setting changes or retry chains.

2. One meaningful cross-depth short gate with existing single-request
engine/tools/dedicated_provider_driver.py and dedicated-gate/compare.py:
1677 fixed input/32 outputs,3+1,same context/cuts/binary/arithmetic, depth2 arm
versus an exactly matched depth3 state oracle. Reuse a matched completed oracle
if it has the identical reset-capable binary/identity; otherwise one controlled
matched control is necessary. Require actual2-head wire availability192B and
READYcapacity2, owner commands/terminals, exact32 IDs, actual canonical pairs,
2065target/73draft canonical sources, seals, quiescence and clean postflight.
Gate must retain its predeclared physical/canonical scope. Depth changes ring/
snapshot geometry and transient head scratch: inventory differences are not
permission to silently drop bytes or call output-only agreement full-state.
If existing comparator cannot express a legitimate registered layout mapping,
record that precise proof gap and stop this arm before a suite speed claim.
No repeated unchanged short gates or new proof framework.

3. After that gate passes, clone the existing runtime-only12prompt suite for
each depth with separate prepared authorities. Keep all original12 prompts,

Provider reset/cold proof and all owner epochs must remain active.

4. Compare every actual output/EOS ID and input hash across depth arms. Bind

Reuse existing validators/pinned CPU receipts rather than new blanket CPU work.
Read existing fresh-changed-cpu/completed-r1-evidence and GPU model proof lineage.

The first complete12prompt arm pair is a useful measured screen; do not treat
one process per arm as a final speed verdict. If material, use preregistered
controlled fresh owner lifetimes for matching repeats (e.g. arm order3,2,2,3,
each suite prompt cold once within its owner lifetime), using existing suite
harness/reset checks. No automatic retries or fault-triggered process cycling.
A tiny/unstable gain closes quickly; do not impose the costly512integration's
10% threshold on this already-implemented configuration lever. A candidate
needs a consistent material suite benefit with exact quality/reset/repeat
identity, not a favorable single prompt or optimistic old work-removal bound.

True gaps remaining
Fixed depth2 has no new native/wire feature gap. Actual reset+full model state
qualification at depth2, matched current3+1 timing and same-output CPU lineage
are still needed. Cross-capacity physical scratch mapping may need precise
review if the existing short comparator refuses; this is a correctness scope
gap, not grounds to weaken it. Per-request adaptive depth or capacity3/request1
remains a separate unimplemented protocol question and is deliberately deferred.
