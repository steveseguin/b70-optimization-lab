# Tiny CPU-native streaming proof and guarded lifecycle

## Question and identity

Can real native token frames reach the SSE client before state disposition,
while retaining SAVE/RELEASE and clean shutdown? This uses the unchanged GNU
HOST_ONLY executable `41cbb6c4ad3bf6626dfba24d3bbd9d95d76b512102e8b94c164e9d421b3c40ca`,
synthetic four-layer geometry, vocabulary16 and context64. It is not the model
or a device execution. The fixture facade deliberately cannot impersonate the
production chat service's tokenizer identity.

## Outcome

**Passed in one execution:** two streamed requests produced eight exact synthetic
tokens through one tiny owner. The first request saved its state, the second
released its state, then QUIT closed the owner at two of its eight allowed
requests. Exit status was0, with no retained resource or incident signal.
Independent audit verified the native inputs/results, all eight callbacks,
SSE text/usage, control ordering and all21 checkpoint binary hashes.

Both clients observed nonempty text before the corresponding disposition.
Finish/usage and `[DONE]` followed disposition. This is an observed event order,
not a latency or throughput claim. All source preparation passed14 CPU checks.

The separate additive streaming lifecycle passes27 CPU checks and independent
review, using actual Python service/codec/HTTP modules with a synthetic native
front/store. It accepts only its own exact streaming server class and unchanged
canonical RunAdmission. The old lifecycle and its exact-class gate remain intact.

## What worked

Actual native token callbacks ran while the front was still `running`, before
terminal consumption. The real pinned decoder mapped the tiny IDs to text, and
the production nonblocking SSE transport delivered those bytes. The first saved
state occupies39,780 bytes and preserves the pending-token representation.
Native MockDevice teardown completed with no live allocation or pending reply.

The lifecycle holds the same service/thread/admission boundary across streamed
RUN and SAVE/RELEASE. Close requests latch until disposition and bounded output
handling finish. Count/idle/deadline boundaries refuse new work; normal closure
calls the owner once. Native/runtime failures retain the original error and
prevent a fabricated normal-close result. A reader disconnect or failed output
observer alone does not cancel native disposition.

## What failed or remains uncertain

No execution failure occurred. Preparation review tightened canonical imports,
fixed interpreter and codec admission before owner creation, partial-SSE evidence,
and cleanup when process/thread status is uncertain. Direct script invocation is
refused because the package's `http.py` could shadow the standard-library package;
the supported CLI uses a qualified module name.

The root invoked the exact reviewed `execute(spec)` after verifying review,
source and plan hashes in a standalone stdin Python process. Only its successful
path was exercised. The CLI's exceptional resource-retention loop is covered by
preparation reasoning/mocks, not by this actual execution. No automatic retry
was performed.

The tiny owner has a synthetic vocabulary/EOS and cannot satisfy the production
StreamingChatService identity. Its actual decoder check is an output-byte mapping
proof, not model-language or chat-template qualification. The27 lifecycle checks
are separate synthetic-front evidence; this tiny proof did not exercise that
production lifecycle. No GPU, daily-application transition or device performance
claim follows.
