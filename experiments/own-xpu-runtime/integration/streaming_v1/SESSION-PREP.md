# Guarded streaming session composition

## Question and identity

Attach the reviewed streaming service and lifecycle to an already admitted model
owner while preserving the canonical profile and all existing ownership checks.
This is an additive factory; it does not start an owner or grant live admission.

## Outcome

The new session passes27 CPU fixtures and independent review. Its additional
49-file source closure binds the earlier64-check component gate and27-check
lifecycle review. The original profile remains16 requests, context4096, full
BF16 state,512MiB parking,256MiB per-save reservation and a768MiB write forecast
above the27GB floor. No resource bound or baseline identity was relaxed.

## What worked

`source_closure()` produces the exact additional source map. Public
`attach(profile, *, streaming_sources, front, store, admitted_argv, launched_at,
last_native_activity, guard)` requires that map alongside the unchanged canonical
profile. It directly composes the new engine, service, lifecycle and server.
It does not invoke the old attach factory and mutate its result.

The raw front/store must be the exact canonical classes. The borrowed process
must have the admitted argv, a fresh zero-count ready state and matching limits.
The held executable and checkpoint-directory FDs must match the admitted paths;
the root must be empty, private0700, owned by the current user and free of aliases.
Launch/activity timestamps remain conservative and unexpired. The actual pinned
codec and guarded store metadata operations preserve model and tokenizer identity.

Existing session locking, receipt handling and parking behavior are retained.
Tests cover mixed SSE/ordinary HTTP, source/review/origin drift, held-file identity,
metadata failures and original-error retention, using CPU fixtures throughout.

## What failed or remains uncertain

No implementation mismatch remains after review. Two canonical fixture cases
needed adaptation to the new streaming composition; they are identified in the
author receipt. Tests intercept profile validation and host observations rather
than claiming current storage headroom or a fresh live owner.

The composition has not served a real model. The separate tiny host proof uses
a synthetic facade because its vocabulary cannot satisfy production admission.
A real device pilot still needs its own plan, client evidence, source seal,
storage forecast and controlled application window.

## When to revisit

Prepare a bounded model streaming client and execution adapter around this
composition. Restore adequate disk headroom through verified retention of closed
artifacts before live admission. Compare streamed tokens/text with the existing
ordinary-response oracles and require clean owner closure and physical drain
before a single restoration of the daily applications.
