# Proposed postreply checkpoint operations

Status (2026-10-23): design only. Packet197 is frozen for its one-owner device pilot. This note changes no native source, binary, checkpoint, qualification label or service. A successor would need its own source/binary pins, CPU gates and device lifecycle qualification before serving integration.

Add a small, explicitly versioned control phase after each reply so ctxkeeper can choose a checkpoint ID using the completed reply tokens. Keep the model and expert cache resident. Reuse the existing checkpoint writer, verification and locks. [Parking.park](../../../../tools/ctxkeeper/parking.py) lines 137–159 computes its ID after generation and calls `Engine.save(id, tokens)`, while packet197 chooses the save ID in RUN before generation.

The relevant current hooks are:

Introduce a command variant and a separately bounded control phase. Preserve the 262144-byte frame bound, safe IDs, pollable idle deadline and signal handling. |
| Generated `main.cpp` lines 2040–2068, represented by the [sealed overlay patch](../../stage2/packet197-warm-request-front/native-request-front.patch) | The next RUN resets state. Dispatch control operations before copying startup options or calling `p58_reset_request`. |
| Generated `main.cpp` lines 2222–2235 | The existing save block constructs processed history and parent lineage. Retain exactly those values outside the request-local scope, even when RUN requested no immediate save. |

| [NativeFront](client.py) `request`/`close` | Add explicit pending-disposition state and SAVE/RELEASE/INSPECT/DELETE methods. Unexpected events still poison the channel; no retry or owner restart. |

Generated line references describe the exact packet197 overlay sealed in `READY-FOR-DEVICE.json`; they are navigation aids, not permission to edit that packet.

Retain one descriptor after successful generation: request ID, original input/prompt vector, exact processed history H, pending token t, tokenizer identity, parent checkpoint ID and manifest hash when restoring, and the engine/model/context identity. Build H using the current save block: fresh/append uses input plus generated tokens except the last; same-generation resume uses restored history plus its old pending token plus new generated tokens except the last. The last generated token becomes t. Device buffers alone cannot reconstruct these host values. At SAVE, compare the caller's supplied tokens exactly to H+[t], recheck the native position/history/sticky-error conditions, then pass the retained original prompt/H/t/lineage to `checkpoint_save`. Never step t merely to make the checkpoint match the caller's token count.

Proposed local protocol v2, using tab-separated fields and LF:

```text
SAVE     operation-id  completed-request-id  checkpoint-id  full-visible-token-ids
RELEASE  operation-id  completed-request-id
INSPECT  operation-id  checkpoint-id        metadata|full
DELETE   operation-id  checkpoint-id
```

RUN retains its current spelling and bounds under a new negotiated protocol version. SAVE is legal only for the current pending descriptor and a fresh safe checkpoint ID; RELEASE deliberately discards that descriptor without deleting any saved checkpoint. A new RUN is refused until SAVE or RELEASE resolves the previous reply. This removes ambiguity about which live state `Engine.save` addresses. The adapter serializes generation, `Parking.park`, and disposition under one owner mutex. It cannot service another session's RUN between a reply and its SAVE. On a parking-policy decision not to save, it sends RELEASE. Only one SAVE is allowed per completed request; there is no overwrite or automatic retry after an ambiguous acknowledgement.

After the final permitted RUN, stay in awaiting-disposition with a bounded deadline. Accept its SAVE or RELEASE, acknowledge it, then drain automatically. EOF/QUIT/signal/deadline can instead discard the unsaved descriptor and drain once. Do not reuse packet197's immediate `count == maximum` exit. Require a separate explicit command-count budget (for example at most four control commands per admitted RUN plus a fixed small session allowance), unique operation IDs and the existing absolute owner deadline. A malformed command or unexpected native/I/O failure halts intake. Typed `missing` and `in_use` control outcomes are normal refusals, never permission to restart.

Emit short JSONL events such as `checkpoint-saved`, `checkpoint-inspected`, `checkpoint-deleted` and `request-released`, each bound to its operation ID and relevant request/checkpoint ID. SAVE completion means the manifest rename/fsync and a consistent metadata snapshot have succeeded; include the manifest SHA256 and an owner-root-relative snapshot receipt. That snapshot lets `Engine.save` construct its policy view even after final-request drain. Keep raw tool stdout off the protocol stream. INSPECT should copy the raw manifest, tokens.bin and next_token.bin into a bounded operation snapshot **while one native shared lock is held**, then return a bounded receipt reference and digests. Running metadata-inspect, releasing its lock, and separately reading payload files would allow a delete/replacement race. Metadata mode must continue to report that state blobs were not fully verified. Full mode retains the existing full byte checks. Neither inspect nor delete should allocate/upload model state or call the device; only SAVE touches the existing owner's state.

DELETE validates the safe ID under the fixed startup root and preserves the existing exclusive, nonblocking lock, revalidation, closed-file removal, fsync and lock unlink. Return `in_use` for lock contention. Return `missing` only for a proven absent checkpoint, not for malformed metadata, symlinks, partial directories or arbitrary I/O failure. Never accept a caller path or implement deletion with a generic recursive filesystem operation. CPU-only management operations must have bounded result sizes/time and cannot reset the pending live descriptor.

Three compatibility changes must be explicit before connecting the policy:

1. **IDs remain exact.** `Parking.checkpoint_id` currently returns `session + '-' + prefix_hash(tokens)[:24]`, where prefix_hash is SHA256 of a compact JSON integer array. This is not the native binary-payload digest. Keep that exact ID in the native manifest; do not silently truncate, sanitize, rename or replace it with a different hash. The current native safe-ID rule is 1–64 ASCII characters, alphanumeric first, no `.lock` suffix. Under the existing policy, admit safe session components of at most 39 characters, or separately design a recorded namespace mapping. Invalid sessions refuse before SAVE.
2. **Token representations remain distinct.** Native tokens.bin contains H as little-endian 32-bit IDs; its SHA256 and manifest position describe H. Parking sees H+[t] and hashes compact JSON. [CheckpointView.parking_metadata](../checkpoint_bridge.py) already provides a distinctly labeled policy projection, retains the native token-state/hash and original manifest bytes, and exposes the full visible prefix. Extend that bridge explicitly for the successor's admitted identity; do not rewrite a native manifest into parking form. Native restore must still repeat full validation before upload.
3. **Qualification is not inherited.** `Parking.compatible` currently accepts only `experimental` or `qualified-one-card`; the bridge currently accepts only p181 `qualified-one-card`/`v1.2+p181`. Packet197 uses `experimental-warm-front`/`v1.2+p197`, and a successor binary will have another exact SHA256. Add an explicit allowlist keyed by the admitted successor label/contract/identity, leaving the p181 path and rejection tests intact. Do not relabel the new engine as p181, accept a checkpoint's self-claimed identity, or bypass native exact-binary checks. Old packet197/p181 checkpoints are not automatically portable to the new binary.

Parking budget remains policy, not host admission. SAVE can transiently coexist with the old checkpoint until the new manifest is visible; reserve that peak before writing. Account for checkpoints retained after `in_use`, partial/ambiguous receipts and filesystem metadata as well as blob sizes. Current `park` saves before eviction and never evicts its kept session, so an oversized new state or in-use old state needs an explicit no-save/refusal decision; do not weaken the root free-space floor. Existing same-ID shortcut should inspect/revalidate the parked object before claiming it still exists. These are small policy checks needed before a live adapter, not changes made by this note.

The adapter's `Engine.save(id, tokens)` uses its recorded last-completed request ID, sends SAVE, verifies the completion/manifest binding and returns a bridge policy view. `Engine.inspect` returns that view or proven missing. `Engine.delete` returns the typed status. The existing `Engine.restore(id, tokens)` signature has no generation cap; define it as a validated pending restore plan consumed by the next explicit RUN (with a matching token vector and cap), rather than secretly starting decode. The runtime still owns compatibility and actual restore. OpenAI rendering/tokenization parity and cancellation stay separate integration gates.

Before a successor device proposal, extend the existing [C++ parser probe](../../stage2/packet197-warm-request-front/tests/protocol_probe.cpp), [transport tests](test_client.py), [bridge tests](../test_checkpoint_bridge.py), and [parking tests](../../../../tools/ctxkeeper/test_parking.py):

- actual C++ SAVE after a reply, final-request SAVE before drain, RELEASE/QUIT/EOF/idle/signal, command budgets, oversized frames, duplicate operation IDs, stale/wrong request IDs, wrong H/t, traversal/symlink/overlength IDs, existing checkpoint refusal and poisoned-channel behavior;
- one tiny host owner: fresh A → postreply save → B → restore A/append → postreply save, with tokens/state equal to the unchanged immediate-save and uninterrupted references; actual snapshot locks, `in_use`, partial/corrupt metadata and no delete outside the root;
- policy hash versus native payload hash, pending EOS handling, exact token/identity/label rejection, explicit successor-contract fixtures, peak disk reservation, repeated-ID inspection and retained in-use accounting;
- actual production argv interception and source/binary closure, then a separately admitted real-model one-owner lifecycle. No speed headline follows from session reuse.

No implementation packet or launch is requested by this note. The next concrete change is the command-state/retained-descriptor extraction and host-only tests after the packet197 pilot result is closed; serving wiring follows successful successor qualification.
