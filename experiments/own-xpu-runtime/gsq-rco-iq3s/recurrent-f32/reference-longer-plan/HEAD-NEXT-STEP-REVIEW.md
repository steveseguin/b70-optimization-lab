# Head diagnostic applicability to first divergence

The proposed dual-store head is a useful diagnostic, not a fidelity correction. Keeping the original BF16 output and argmax while additionally retaining the same pre-conversion float can isolate the final store's effect on this native head input. It cannot assign native/reference differences to the final store alone: upstream BF16 activations, quantized CPU activation packing, reductions and nonlinear math differ. A new behavior-changing F32 head is a separate baseline and must not be presented as the diagnostic.

The three-prompt harness detects a first differing output ordinal only after the current request finishes (up to512 outputs), then refuses the next request. Its final bundle contains the head from the **last evaluated position**, not necessarily the first divergence. If outputj differs and later tokens were generated, the final head sees already-diverged context. It cannot be compared to the CPU's last probability row as a same-prefix error measurement.

If a divergence occurs, preregister a separate bounded shared-prefix diagnostic at `original_prompt + CPU_output[:j]`, generating exactly one next token. At the first differing ordinal the native output prefix beforej already equals the CPU prefix, so this recreates the conditional input IDs. Reusing a later free-running native prefix would not. Preserve the original failed longer attempt; neither change its token gate nor silently finish the remaining prompts. Root decides the separate diagnostic run.

The closed CPU3 authority80895690 reports512/512/334 probability rows for512/512/334 output IDs, with no omissions. Given the audited ordered-subsequence identity and equal cardinality, each current row aligns with its output ordinal. Therefore the first-divergence CPU row can be used directly from these retained responses if the index exists. This does not generalize to a future response with missing UTF8 probability rows: then repeated IDs may make positional alignment ambiguous, and a separately admitted one-token reference request is needed to obtain an unambiguous conditional distribution.

Interpret the dual store by reporting original BF16 argmax/ties, unrounded native FP32 argmax/ties, and reference selected token/top32 on that common prefix. For finite ordinary values, rounding to BF16 is monotone: its most direct argmax effect is collapsing close scores into ties, whose tie-breaking must be checked against the actual compiled argmax. If preserving the float changes the winner to the reference winner, that is evidence that the last store mattered at this position; it does not establish broad quality or isolate all distribution error. If it does not, upstream or head arithmetic remains implicated. Do not select an acceptance tolerance from the observed differences.

The proposed additional993,280B rank1 observation buffer is small but must be included in allocations, readback and captured artifact forecasts. Reset validity and mark it valid only after the actual head event and committed target boundary. For this target-only diagnostic there is no reason to support speculative validity initially. Keep both original BF16 writes and their exact control tokens/state as a gate: source-equivalent float expressions can still compile differently when adding stores/register pressure. The single-entry dependency argument is plausible but remains a build-time dependency/object closure obligation, not unconditional39-object reuse authorization.

No head implementation, new compiler invocation, model/device run or payload read was performed for this review. Longer independent target comparison remains the immediate evidence priority. Even if all three token sequences agree, no broad quality promotion follows and the already-observed numerical gap remains disclosed.
