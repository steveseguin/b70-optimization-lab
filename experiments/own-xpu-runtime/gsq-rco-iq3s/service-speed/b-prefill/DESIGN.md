# Lossless batched prefill design for corrected SC117

**Decision: the weight-sharing idea is arithmetically sound for independent projection rows, provided each row retains the exact current instruction-level arithmetic sequence. It is not yet a device-proven full-engine transformation.** Batch the projections and row-local operations; keep recurrence, causal cache updates and draft updates sequential initially. Full-state compatibility requires preserving scratch and alternate-bank bytes as well as model outputs (`DENSE/block.hpp:27-41,71-76`; `NATIVE/p33_candidates.hpp:85-100`; `RANK:250-257`; `INVENTORY:6-27`).

This is research/design only. No build or device test was performed. The fixed oracle is binary **5926a24746c62c6b0ecdc5c3e4895f310145e0f9d74a90a5d657035b9a8151f4**, with every checked source dependency matching its receipt (`BUILD:1223`; `source-audit.json:1-8`). Never use the older BF16-state oracle. Exact parity preserves this corrected engine; it does not resolve the separately recorded independent-reference token71 mismatch (`L/recurrent-f32/operating/longer-a/RESULT.md:3-9`). No tolerance, ULP budget, token-only waiver or silent precision change is proposed.

## Highest-value first stage: one p33 multirow projection prototype, under one day

Build an isolated **variant6 expanded-weight multirow projection kernel**, first for the 22 Q6 GDN-QKV sites (K2560,N10240), then the same implementation for all 48 Q8 output projections (K6144,N2560). The source bodies are shared in `NATIVE/p33_candidates.hpp:77-104` and instantiated by `NATIVE/p33_submit.cpp:86-94`; dispatch and geometry are fixed in `DENSE/generic_engine.hpp:38-43`. This stage touches no recurrence, attention, controller or MoE scheduling.

These sites account for **720,896,000 + 849,346,560 = 1,570,242,560 distinct weight bytes per target position**, 29.4753% of the corrected target-layer inventory; see `calculations.json:18-26`, the exhaustive `kernel-sites.tsv:1-1872`, `NATIVE/p33_candidates.hpp:85-93`, and `EXPANDED:11-21`. With B=8 sharing and every other weight read unchanged, the ideal whole-target weight-byte ratio is `W/(W - W_selected*(1-1/8))`, about **1.3475x**. This is only a byte ceiling; neither the affected measured class time nor a service speedup is established. QKV's aggregate historical class contains other quantizations, so assigning its entire measured time to these22 sites would be invalid (`MAP.md:94-131`).

Proposed one-day budget: 1h bind existing immutable weight/activation fixtures and oracle identity; 2h implement the two template instantiations with B1/4/8; 1h strict build/review; 2h bounded device comparison and timing; 1h readback/localization/closeout. This is a seven-hour engineering estimate, dependent on an already available isolated device test window and existing payloads. It is **not** a promise to deliver a full batched controller in a day. No such window or work is started by this report.

For the discriminator, compare M16/32/64 and partial tails against repeated unchanged p33 variant6 submissions using varied retained BF16 activation rows. Check every BF16 output byte, then hash all original target-state buffers before/after the isolated operation to establish that it did not alter target state. The operator oracle must also reproduce the saved outputs of the unchanged5926 engine for those retained rows, not merely agree with a newly compiled reference. Device outcomes remain pending. A microkernel pass authorizes the next design stage only; full tokens/full-state qualification remains mandatory below.

Proposed performance decision: require at least 1.5x median operator throughput for B4 or B8 on the registered shapes, with no byte mismatch, after two independent fresh test owners. Stop expanding geometry once the gate passes; if it fails, retain the evidence and inspect instruction/register traffic before wider integration. This threshold is a project choice, not existing evidence. B16/32/64 is a later occupancy experiment, not a prerequisite to learn whether reuse pays.

## Why independent rows can be bit-identical

For an output feature j and position p, write the current scalar work as the vector of32 lane accumulators followed by its fixed tree. The new kernel retains exactly the same weight bits, BF16 input bits, lane-to-k assignment, FP32 product, FP32 add, tree edges and BF16 output conversion for that (p,j). Moving a load outside the loop over p changes no arithmetic operand. By induction over each lane's k-sequence, all accumulators match; by induction over tree width1,2,4,8,16, the result matches. This is a source-level proof obligation grounded in `NATIVE/p33_candidates.hpp:85-100`, `NATIVE/p33_submit.cpp:53-65` and `DENSE/block.hpp:31-39,75-76`.

The argument fails if a compiler contracts multiply/add, reassociates the reduction, uses different dequantization, rounds an intermediate differently, spills through a reduced-precision buffer, or if a row reads overwritten state. Preserve the receipt's `-fno-fast-math -ffp-contract=off`, IEEE denormals and precise FP32 divide/sqrt (`BUILD:10-18`). Device byte comparisons are still required, including signed zeros, exceptional fixture scales and NaN payload behavior; never canonicalize a mismatch. Strictly higher-precision experiments would create a separately reviewed baseline and are outside this bit-identity design.

## Concrete kernel interfaces and work-group mapping

Proposed interfaces separate position count M from output features N and expert slots. Existing `Matrix.count` is not to be silently reinterpreted as a prompt batch (`DENSE/block.hpp:82-87`; `NATIVE/p33_submit.cpp:51-55`). These are signature sketches, not compilable code:

```cpp
template<Type T, unsigned K, unsigned B>
Event dense_positions_v6(Queue&, const uint8_t* W, size_t weight_row_stride,
    const uint16_t* X, size_t x_position_stride,
    uint16_t* Y, size_t y_position_stride, unsigned M, unsigned N, Dependencies);

template<unsigned PackedType, unsigned B>
Event packed_positions(Queue&, const uint8_t* W, size_t weight_row_stride,
    const uint16_t* X, size_t x_position_stride,
    uint16_t* Y, size_t y_position_stride, unsigned M, unsigned N, unsigned K,
    Dependencies);

Event ordered_state_positions(Queue&, const RowBindings* rows, unsigned M,
    unsigned first_position, LegacyBankPair, LegacyWriteback, Dependencies);

Event grouped_expert_positions(Queue&, const ExpertSegment* stable_groups,
    const RowSlot* original_position_and_slot, unsigned routed_pairs,
    const WeightBank&, const PositionInputs&, SlotOutputs&, Dependencies);
```

For both dense signatures use `nd_range(global=ceil(M/B)*N*32, local=32)`, required subgroup32. WG id identifies `(position_tile, output_feature)`. Every lane holds `float acc[B]`, initialized to positive zero as today. For p33, loop `tile=lane*8; tile<K; tile+=256`, then j0..7; load/decode the weight once, then update each valid position's accumulator with separate product/add. Apply the original adjacent-lane tree to each accumulator, then the original BF16 conversion. Current variant6 is Split1; no new split-K is permitted (`NATIVE/p33_candidates.hpp:85-100`; `NATIVE/p33_submit.cpp:63-65,86`). For packed types, use the different current `(block,group,lane)` sequence and exact format decoder (`DENSE/block.hpp:27-41`). No cross-position reduction occurs.

A larger logical M does not increase guaranteed weight reuse if B stays4 or8. Independent workgroups reload their weight rows. B64 means64 live accumulators per lane and may spill or reduce occupancy; it must earn its place through measurement. Mask only positions outside M; inactive lanes must still participate in subgroup shuffles. Pointers/strides must be checked for aliasing, extents and overflow before submission. Keep an M1 fallback using the original operator.

## Arithmetic that a batched version must retain

**Packed dense and IQ3 expert rows.** `DENSE/block.hpp:27-41,71-76` uses one 32-lane workgroup/output; lane l walks block b then group g, k=256b+32g+l. Each product is FP32, followed by an explicit FP32 add; tree widths 1,2,4,8,16 are adjacent lane additions; a single BF16 conversion writes the row result. `PACK/packed.hpp:16-21,46-52` and IQ3 block's `L/recurrent-f32/build/source-v2/experiments/own-xpu-runtime/gsq-rco-iq3s/expert-iq3xxs-block/engine/build/source/block.hpp:16-27,54-59` follow that same lane sequence, with their exact format decode. A new `template<T,R> batched_packed(W,X,Y,M,K,O,x_stride,y_stride)` can use one 32-lane WG/output and token tile R, with private `float sum[R]`; decode each weight once, then for r=0..R-1 do `product=weight*bf16(X[r,k]); sum[r]=sum[r]+product`. Apply the original lane tree independently to each accumulator. This shares loads/decode across R, not magically across M when R<M. M16/32/64 need register/occupancy measurement; R4/8 is a sensible first microkernel. No FMA, reassociation, BF16 product, matrix instruction, or split-K change.

**Expanded dense p33.** Its lane walks k=lane*8+256*t, then j=0..7, **not** k=lane+32*t (`NATIVE/p33_candidates.hpp:85-100`). Keep `value=scale*code; product=value*input; sum=sum+product` and the 32-lane adjacent tree, with Split=1 in the currently admitted variant6 (`NATIVE/p33_submit.cpp:53-64,86`). Sharing W across token accumulators is compatible in principle; treating this as a generic packed kernel silently changes summation order. A signature analogous to `batch_expanded<T,R>(W,X,Y,M,K,O,strides,variant6)` needs the current row stride and distinct codes/scales offsets. Never use four split-K partial sums, tensor cores or a vendor GEMM as an identity substitute.

**HC.** Rank-independent rows can be batched, but the four stream terms inside each row stay ordered. HC mix is `sum=0; for h=0..3 sum += sigmoid(gate[h])*norm[h]; bf16(sum/4)` (`NATIVE/kernels.hpp:159-162`); combine is `bf16(stream + branch*(2*sigmoid(inject/4)))` (`NATIVE/adapter.cpp:142`). Preserve down/up output BF16, SiLU/4 BF16, and the current norm's two-stage specialised reduction and scratch tree (`NATIVE/dispatch.hpp:14`; `NATIVE/specialised_submit.cpp:31-47`). This is not the unused legacy fused-HC arithmetic.

**MoE.** Routing remains independent per row: 512-way probabilities, top10 tie break by lower expert ID, normalized selected probabilities (`NATIVE/adapter.cpp:151-162,193-203`). Stable grouping by expert is allowed only as a schedule transformation; record `(position,original_slot)` and scatter outputs to those slots before the original combine. Keep gate/up/down per-row dot order, per-output BF16 and SiLU boundary. The actual combine has two kernels: `DENSE/main.cpp:1575-1576` invokes `mixture`, then `DENSE/main.cpp:1497-1498` substitutes that BF16 mixture and scalar1 into the shared-branch combine. `NATIVE/performance.cpp:71-72` selects `iq3::kopt4::epilogue`; its contract is explicit FP32 product/add in slots0..9 then BF16 (`NATIVE/../packet9-kopt4/reference.hpp:16-24`), followed by the existing shared-branch BF16 boundaries (`NATIVE/kernels.hpp:162`). Keep slot order; no atomic accumulation in expert execution order. Uniform independent routing would give U(M)=512*(1-(502/512)^M) distinct experts; effective weight reuse10*M/U is only ~1.15/1.34/1.75 at M16/32/64, not M. This is a hypothetical overlap model, not a measured routing distribution. Reuse must be measured from retained real routes.

**GDN/conv.** `ng::Shape.tokens` already exists; `NATIVE/kernels.hpp:127-149` explicitly loops positions inside each state-owning workgroup/channel. `L/recurrent-f32/recurrent_policy.hpp:10-11` rejects nonzero implementation for F32 recurrence; generic corrected ng is required, while the older specialised GDN still uses BF16 accessors (`NATIVE/specialised.hpp:130-136`). Do not reuse that old specialised path. Within GDN one WG owns `(value-head,output-dimension)`, preserving dot128's 4 adjacent products per lane and 32-lane tree (`NATIVE/kernels.hpp:108-110`), F32 state after each position, BF16 emitted y. Conv history remains F32; GDN conv has dilation1 and PLE dilation3 and different pre-SiLU BF16 rounding (`NATIVE/kernels.hpp:145-149`). No parallel scan, chunk algebra, or reassociated recurrence.

**Attention.** Start with per-position unchanged prepare/pool/select/split32 attention calls while batching only projections. The actual attention is `p49::Attention<0,1,2>` → admit/tiles<true>/combine<true> (`NATIVE/p49_qsa_submit.cpp:31-33,49-50`), with a fixed32 tile softmax and fixed per-tile tree (`NATIVE/p49_qsa_kernel.hpp:47-77`). Generic softmax is not an identity substitute. `NATIVE/p49_qsa_submit.cpp:39` admits at most2 positions and its scratch offset is hardcoded +16 (`:30`), so widening the limit alone corrupts counts for M>4. A future M version must reserve aligned 4*M counts and unchanged M*24*ceil(launch_slots/32)*258*4 partial bytes, while retaining the per-position count/order. KV remains BF16. Pool only finalizes groups of4; select sees floor((pos+r+1)/4) groups and appends the incomplete-group tokens (`NATIVE/kernels.hpp:181-201`). Source suggests completed future pools can be ignored by smaller row prefixes; nevertheless first integration keeps pool/select/attention sequential because full-state scratch tails and prefix-specific availability must match, and a causal mask alone proves neither.

**State banks and dump identity.** The current full dump includes every plan allocation, including overwritten intermediates, plus alternate recurrence/history banks (`RANK:253-257`). Rank0 swaps after each half (`RANK:204`), so a batched final-only recurrent update is insufficient: preserve the serial penultimate state/history in the correct alternate bank, exact M parity, last-row values for every old per-layer intermediate, same keys/values/raw/pooled tails and IDs, token/history/position/error/status, and stale head values on skipped-head chunks. The existing ng multirow loop writes final recurrence only; add a separate penultimate capture or preserve the exact per-position bank schedule. Matching only emitted tokens or final streams does not satisfy the contract.

## MTP is not last-position-only

The draft consumes the preceding target's four final hidden streams plus the next confirmed input token's embedding (DRAFT:228-233). Every confirmed next prompt position invokes DRAFT, even when its head flag is false (CTRL:94-96). Draft `target_position` must equal private `position+1`; the whole draft layer/attention-cache update runs, omitting only `final.*`/logits/argmax when `head=false`; then draft position advances (DRAFT:228-255). Draft cache outputs include QSA keys, values, raw and pooled vectors (DRAFT:307). Thus skipping early draft steps loses its history and violates both sequence checking and later proposal identity. The draft head is enabled when the confirmed token is the last prompt token (`p+2>=length`), then continues during generation (CTRL:96).

Because this service puts the draft on rank 0, rank 1 exports its final-layer streams through `reverse_offset`, tagged `position+1` (RANK:184-187), and DRAFT verifies that reverse position before copying hidden state (RANK:319-321; DRAFT:231). A batch must retain **every row's rank1 final streams** and replay draft updates in order with exactly the preceding hidden row and confirmed token. Draft mutable allocations are explicitly private and target-alias checks are enforced (DRAFT:199-204), so deferring draft work until a target chunk finishes can be mathematically safe if all required hidden rows survive and the same sequential draft cache updates are performed. It can lose target/draft overlap; do not count that overlap twice in a speed projection.

Suggested first integration retains the last one or two prompt target positions in the unchanged scalar controller, so target head/emission/EOS and the final draft publication are not changed simultaneously. The transition must carry a precisely defined current target position, already-confirmed rank0 candidate status, draft position, draft guess/publication sequence and reverse-row identity; it cannot simply call the original `run` again because that unconditionally primes position 0 (CTRL:65-70).

## PLE/history and HC constraints

`prepare_token` clears lookup IDs, forms host PLE IDs from token and the two previous input tokens, handles EOS by resetting the older token, uses 64-bit wrap/XOR and signed modulo with metadata offsets, then advances `(history0,history1)` (ENGINE:1275-1298). Batch preparation may run this exact host loop over known prompt IDs, retaining per-row lookup outputs and final scalar history; neither floating-point GEMM nor token reordering belongs here. Rank0 also retains device `token_history`, and candidate rollback records the previous 16 bytes (RANK:142-143,198). RESET restores both host and device histories to EOS (RESET:29-35). Hashes must include these, even if all emitted tokens happen to match.

HC input/output streams are four BF16 streams of width h=2560, hence 20,480 bytes per position (RANK:154,185,208; SERVICE:112 configuration). Rank handoffs must preserve their bits; HC does not justify flattening these streams to one or moving its rounding boundary. The exact arithmetic/kernel mapping is covered in the kernel map task.

## Proposed batch protocol (design, not present implementation)

Define a new, versioned `PREFILL_HALF_BATCH` command in an additive controller/transport copy. Do not repurpose HALF or DRAFT. Keep the existing fixed command envelope only as a descriptor to a separate, versioned shared region; require version, start position, positive row count, prompt-only flag, token-array offset/length, forward/reverse stream stride, payload byte lengths, end position, request ID and sequence. Reject speculative batches, noncontiguous positions, overflow, unexpected initial position, tail beyond context, unresolved scalar candidate/draft or aliasing control regions. Perform input bounds checks before submissions. The current Request is 32 bytes, Reply 64 bytes (RANK:15-18), so a full batch descriptor cannot fit without an explicitly versioned ABI.

The current shared mapping totals `4*65536+4096+64=266304` bytes and includes 64KiB forward slots, a publication/control page, reverse region and probe region (RANK:13; TRANSPORT:6-8). A 64KiB forward slot holds only floor(65536/20480)=3 complete stream rows. A single forward matrix requires M16=327680 B, M32=655360 B, M64=1310720 B; preserving reverse hidden rows requires the same again. With independent producer/consumer forward slots plus reverse slot, payload alone is 983040/1966080/3932160 B. Allocate this separately and leave old control offsets intact; do not overwrite the MTP publication/mailbox/probe regions. Explicit descriptor bounds and producer-release/consumer-acquire ownership replace assumptions in `Backend::handover()` (CTRL:44).

For each chunk: prepare token/PLE rows on rank0; run layers 0..23 layer-major; publish rank0 output matrix; rank1 consumes exact rows and runs layers24..47 layer-major; preserve/export every final row; run required draft updates sequentially using these rows; commit chunk only after sticky error/candidate/draft checks. Initial implementation serializes chunks. A later double-buffer pipeline may overlap rank0 chunk k+1 with rank1 chunk k, but rank0's draft shares the device and needs reverse rows, so the ownership schedule must explicitly account for it. Failure poisons the batch and invokes existing cooperative error behavior; no partial-success resume/retry is proposed (RANK:203,373; CTRL:21-26,41).

## Full target state means more than KV

The reference `state_dump` hashes and bundles **all plan allocations including overwrite-only intermediates**, all alternate temporal banks, host history and FP32 cache metadata (RANK:250-257). The additional request inventory hashes all standalone target mutables excluding already represented buffers, weights, pinned slab, immutable snapshot tables and draft-labelled allocations; this includes scratch and speculative reserves, plus lookup IDs, selected IDs, loaded layers, cache source/extent, bank parity, current/alternate launch extent, logical event, history and poison state (INVENTORY:6-27). RESET also records full draft state, whose mutable allocations are hashed by label (RESET:15; DRAFT:301-305).

**One final unchanged scalar token is not a proof that these bytes match. Two final tokens are not a general proof either.** Scratch write ranges differ by operation, and QSA-related ranges are position-dependent; an unwritten tail can still carry an older token's last write (SNAPSHOT:118-150). Running scalar tokens may repair recently overwritten regions and both recurrent banks, but not an arbitrary stale-tail mismatch. No whole-buffer hash may be ignored or zero-normalized after the fact.

Concrete exact-state design:

1. Enumerate the write sets of every old mutable allocation at the actual selected kernel/subpass, including data-dependent extents and scratch. An unknown writer creates a full-allocation preservation dependency: keep its original token-major execution until exact actual write masks and predecessor reads are proved. Snapshot may-write unions are conservative copy bounds, not valid last-writer masks (SNAPSHOT:118-150). Keep per-row computation workspace separate from the legacy scalar allocations.
2. For each legacy byte/typed element, materialize the value from the **last writer in the original ordering** `(absolute position, plan-site, subpass/write ordinal)`. Preserve the prechunk byte if no writer occurred. An implementation can use proven static interval overlays instead of per-byte tags; dynamic sparse writes need explicit writer metadata. This restores the old scalar allocation's final contents even when layer-major execution produces them in another order. Values are copied exactly, never recomputed with a different reduction or zeroed to make a hash pass. Validate each scratch read has the same preceding producer; otherwise keep that operation sequential/shared in the original order.
3. Rank0 temporal banks need the exact final TWO versions. For every GDN/conv layer, sequentially alternate the same physical active/spare pair for each row, starting from the original bank selection. After M rows each layer's pair holds the original `S_(p+M)` and `S_(p+M-1)`; globally change bindings iff M is odd. The existing scalar path swaps after each rank0 HALF (RANK:204), and global swap changes all bank IDs, parity, command caches and FP32 source validity (ENGINE:1161-1167). Do not globally swap during just one layer's row loop. Preserve the third reserve untouched during non-speculative prefill; reserve rotation occurs on speculative snapshot begin (SNAPSHOT:401-415; ENGINE:1150-1158).
4. Match both context extents at boundaries crossing 32-token buckets. The scalar engine admits `min(context,ceil((position+1)/32)*32)` (ENGINE:1644-1658); active/alternate extents follow their respective bank cache pairs (ENGINE:1143-1147). A batch-wide larger extent must not change an earlier row's attention iteration bound or its final metadata.
5. Keep logical event accounting as the number of original logical plan-site visits, even if physical kernel submissions are combined. It is incremented once per `issue_site`/`enqueue`, not intrinsic hardware work (ENGINE:1681-1694,1696-1723). This preserves the existing inventory value; physical launch counts remain separate new telemetry.
6. Preserve legacy allocations and hash all of them. ## Exact scalar-controller seam (proposed)

For service MTP mode3 with draft_rank0 and overlap enabled, let prompt length be P>=3 and bulk target prefix length N=P-2. The bulk phase consumes target positions 0..N-1 on BOTH ranks. Replay the draft at confirmed positions 1..N-1 using the matching prior rank1 hidden row; all of these have head=false. Retain rank1 hidden row N-1. Before the seam, execute and ACCEPT the original scalar rank0 HALF at position N, then execute the original rank0 DRAFT with confirmed token prompt[N], target_position=N, head=false and the retained rank1 hidden row N-1. This is the old loop's state after iteration p=N-1: rank0 is one position ahead, rank1 is committed through N-1, the draft has advanced to N, and its publication for position N+1 is ready. The ordering follows CTRL:82,87,94-97 and RANK:319-321. P<=2 uses the unchanged scalar path.

Introduce an explicit `Resume` record rather than invoking `run` from position0: next iteration p=N; rank0 stream row for position N; rank0 position=N+1 and rank1 position=N; no pending candidates; draft private position=N; draft_pending=true with draft_sequence=N, Publication.sequence=N and Publication.position=N+1, and publication polling already completed; history contains prompt[0:N]; no emitted tokens/guesses yet; out.start is original request start; current logical counts, bank identities and context extents preserved. Resume the original loop body at p=N, which processes the final two prompt target positions N and N+1=P-1. The head flag for the subsequent DRAFT at target_position=P-1 becomes true exactly as CTRL:96 prescribes. No modified head, first-token emission or speculative-decoding logic is needed in that suffix. For target-only mode0, use the same two-rank target positions but omit every draft replay, leave draft state untouched and set draft_pending=false. For MTP rank0 the sequence must be N specifically: CTRL:73 expects uint32_t(p), CTRL:36 sets the local draft request sequence to its position, and DRAFT:265-281 completes the publication/position advance. Other draft placements or overlap modes require separate seam definitions and gates.

A canonical comparison boundary is this named resume phase: both ranks drained, all candidates accepted, rank0 consumed N+1 inputs, rank1 consumed N, draft consumed N confirmed transitions with its publication ready. For the intermediate oracle, use an isolated diagnostic host driver of the unchanged binary's existing HALF/ACCEPT/DRAFT/DUMP commands, executing the SAME scalar-loop phase and then quiescing; never compare rank0 and rank1 at a fictional equal position if the scalar sequence is already one ahead. Label intermediate diagnostic command schedules separately from the unchanged native-controller end-to-end run. The unchanged binary's existing end-of-request DUMP provides the final oracle; no edit to the running service or frozen sources. Invoke the existing full-inventory DUMP convention (RANK:365) at matched quiescent boundaries in both compared arms.

## Preserving two-card overlap after the identity skeleton

Proposed steady schedule: rank0 computes target chunk k+1 while rank1 computes chunk k. Rank0 then computes chunk k+2. Draft execution uses saved rank1 hidden rows, not the current rank0 target streams (DRAFT:231-233), and consumes confirmed input tokens in their original order (DRAFT:229). ## Roofline calculations: projections, not measurements

The corrected strict target-only weight join (`card0:weight:` prefix, excluding `card0:draft:weight:`) derives **5,327,311,360 B** unique addressed target-layer weights per scalar position: rank0 **2,649,294,080 B**, rank1 **2,678,017,280 B**. Source and calculation detail: `kernel-notes.md:33-74`, `kernel-sites.tsv`, and the corrected source/census joins identified there. This corrects an intermediate draft/target-name collision; old5.373GB totals are invalid. These are optimistic unique addressed-byte counts, not DRAM counters. Intermediate prompt positions already skip the839,321,600 B target output head; do not credit removing it as a new gain (`kernel-notes.md:74-80`).

Let logical chunk length be M and actual register/SLM sharing row tile be B. A multirow kernel with independent work-groups for B-row tiles can guarantee at most **B-fold common-weight reuse**, even if M is64. It cannot claim M-fold reuse from caches across work-groups. Expert traffic depends on overlap: for independent uniform top10 of512 routes, expected distinct experts within B rows are `U(B)=512*(1-(502/512)^B)`. Actual routes are unknown and this is an explicit workload model; worst-case `U=min(10B,512)`, identical-route best case `U=10`. Every selected slot keeps its own original arithmetic. Top10/512 and the per-position slot behavior are sourced in `kernel-notes.md:37-74`.

Ideal bytes per row `W(B)=W_common/B + W_expert*U(B)/(10B)`; bandwidth-only speed ceiling `W(1)/W(B)`. If effective bandwidth is beta GB/s, ideal weight time per row is `W(B)/beta` nanoseconds, subject to unchanged arithmetic/issue and sequential-state floors. No external peak bandwidth is assumed.

## Performance gate and evidence still needed

The roofline is a planning model, not a measured speed claim. In particular its f=.30 unchanged-time assumption covers existing residual work only. Serial recurrence, QSA, unbatched experts/HC as applicable and MTP body must be measured; lost two-rank overlap is a separate new scheduling penalty, as quantified below. Before a service prediction, collect corrected per-class or per-site evidence in a future authorized experiment; the current corrected files are empty and the old class profile mixes214 prompt/decode positions (`MAP.md:86-96`). Compare complete cold realistic prompts once per run, cached_tokens=0, BF16 KV and the unchanged target, two fresh owners, with TTFT/prompt wall and decode reported separately. Exclude reset, load/JIT and profiling from steady-state prefill measurements while reporting them separately. Do not infer performance by summing rank times or by turning warmed kernel diagnostics into a public benchmark (CTRL:81-97; MAP.md:124-131).

Initial integration serializes chunks to simplify identity. That sacrifices the current rank0/rank1 overlap; the target-only per-rank means are24.417/23.762ms, so a serialized two-rank design must beat its extra critical-path cost rather than assume an automatic gain. A later explicit double-buffer schedule is needed to exploit both cards continuously, and rank0 draft work competes for that same device. Require measured critical-path/transfer times before retaining the illustrative1.5–2.1x planning band (CTRL:74,82,94-97; timing-memory-notes.md:42-49). If batching cannot recover the lost overlap, the correct conclusion is a failed schedule, not a lossless-speed claim.

### Separate cost of losing rank overlap

The unchanged-fraction formula above cannot absorb a *new* serialization penalty: with unchanged kernels it otherwise predicts1x despite changing the schedule. Using only the corrected target-only half means as an idealized two-stage sensitivity, `lambda=(24.4170918+23.7624647)/max(24.4170918,23.7624647)=1.97319`. Thus a completely serialized chunk schedule has `S_net=S_work/lambda`: the illustrative1.538–2.105 work speedup becomes **0.780–1.067x**, and the B8/c=.25 example becomes about **1.030x**. These are not actual service predictions: the raw means cover a different short target-only request; real MTP, copies, context and startup costs differ (`/mnt/usb-models/own-xpu-runtime-results/gsq-recurrent-f32-b/prompt-00-none/rank0/timings.jsonl:2-86`; sibling `rank1/timings.jsonl:2-86`). They show why the initial serial schedule is an identity milestone, while a measured double-buffer schedule is necessary before forecasting substantial service gain.
