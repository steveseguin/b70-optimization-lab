## Execution order

1. Context spine: preserve the separate banked short result, then probe 2K → 8K → 32,000 input plus 128 output on one fresh graph-on MTP0 F16 server. Correctness, retrieval, capacity, or runtime failure stops deeper serving probes; speed does not. If 8K is green and the 32,000-input target fails, measure 16K then 24K and publish the serving boundary. Fill 4K/16K/24K probes only after endpoints justify it. These serving probes support estimates but do not directly fill the exact active-context axis; in particular, 32,000 input is not `active_context_tokens=32768`.
2. Eager control: full short benchmark and quality battery at MTP0/F16. If green, add eager 8K and 32K endpoints.
3. Eager MTP2: sensitive canaries, target oracle, and acceptance evidence first. A clean parent expands to the full short battery and exactly one high-value eager MTP4 short actual even if slow. MTP1 and MTP3 remain estimates unless an actual would change the site conclusion.
4. Graph MTP1: the smallest speculative graph dose. A correctness failure quarantines graph-on MTP1–4 for b2dd only. Eager and later snapshots remain open.
5. E4M3 KV: eager MTP0 full battery first. Only a green parent opens graph-on and 32K children.
6. E5M2 KV init: boot and canary first. A specific dtype/init rejection is unsupported; a generic harness failure is merely failed. If it boots, use the E4M3 battery.

Intersections require every relevant parent to pass. In particular graph-on MTP4 requires both the graph-MTP parent and the eager MTP4 actual to be clean. Failed attempts are preserved; a retry gets a new root, cache, port, and `rN` suffix.
