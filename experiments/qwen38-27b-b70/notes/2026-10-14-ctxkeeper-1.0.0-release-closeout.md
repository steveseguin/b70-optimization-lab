# ctxkeeper 1.0.0 release (campaign 19) — closeout

<!-- campaign-closeout -->

## Question and identity

Can someone outside the lab install the context proxy and get the lab's measured results by following its README
alone? `tools/ctxkeeper` was packaged as version 1.0.0 (commit b0b853681: `pyproject.toml` with a `ctxkeeper`
command, a Dockerfile, `--recipe agent|qwen`, a user README, `examples/long_chat.py`, CI) and tested as a user would
run it, on 2026-10-14 between 20:39 and 21:46 EDT: Qwen3.8-27B FP8 on the campaigns' two-card research server
(vLLM, R314 image, 262K window, unchanged recipe) for G1-G3; Gemma 4 26B Q8 on llama.cpp (the lab's LAN service
on its `balanced` recipe, 16K per slot) for G4. Registered in the lab note before the first run
([campaign 19](2026-10-10-context-16k-baseline.md#campaign-19-registered-2026-10-14-before-any-run-the-release-gate-for-ctxkeeper-100)).

## Outcome

**Accepted: released as [ctxkeeper-v1.0.0](https://github.com/steveseguin/b70-optimization-lab/releases/tag/ctxkeeper-v1.0.0).**
Every registered check passed on its valid attempt (c19c for G1-G3, c19 for G4):

| Check | Registered | Result |
| --- | --- | --- |
| G1 freeagent + `ctxkeeper --recipe qwen`, no other option, repair-n40-s2x | fixed 40, clean >= 38, audit >= 6, <= 45 min | fixed 40/40, clean 40/40, audit 7/7, 30 min 54 s |
| G2 `long_chat.py`, 300K tokens, through the Docker image | 4/4 | 4/4, history 304,552 tokens, 4 min 19 s |
| G3 the README's OpenAI SDK snippet | plain + tool call | plain, tool call and streaming all returned in the SDK's types |
| G4 Gemma 4 26B on llama.cpp, `--recipe agent --budget 15360`, 100K tokens | no bar (smoke test) | 4/4, 4 min 28 s |

Quality scope: one run per check, one seed per task, one machine. G4 is a smoke test, not a measurement of the proxy
on Gemma.

## What worked

- `--recipe qwen` alone matched the hand-tuned repair runs: no `--recite-when` was needed on the repair task, whose
  tickets arrive in tool results; the rules held from the notes the model sees each turn (R1 38/38, R2 33/33,
  R3 27/27). 91% of the notes calls' prompt tokens came from the server's prefix cache.
- The Docker image (189 MB, built from the 78 KB source archive) carried a conversation longer than the server's own
  window (304K against 262K) with 24 in-place cuts and none failed.
- The same proxy in front of a different model and server family (Gemma on llama.cpp, `--recipe agent`) kept the
  codename, the starting budget said before 16 cuts, the current budget and the standing rule.
- Distribution without the 2 GB repository: a GitHub release holding the wheel, the source archive (a Docker build
  context and a pip source), the two program files and the demo, with SHA-256 sums.

## What failed or remains uncertain

- **Two voided attempts, both host memory beside the research server, neither the proxy:** c19 (a model download,
  about 1 GB resident, ran beside the server; the 1.6 GiB guard fired at the first agent request) and c19b (a
  one-off GGUF header read of mine misparsed the file and allocated without bound during the server's start). The
  runner now refuses to start while a `dl-*` download unit is active.
- One notes reply in G1 was not applied ("NOTES over twice the cap after the changes", two minutes before the end);
  the proxy held the cut and continued, as designed. Not yet known whether a long enough task would hit this often.
- Not measured: other models' quality through the proxy, a widely used third-party agent (the owner's pick is still
  open), more than one conversation at a time, and the third-loss check rule (bb14da05a) live.
- Closed before the release, offline: a cross-counter notes check (0 of 9 wrong lines caught, 5 right lines
  questioned); patch kept, DO-NOT-REPEAT row.

## When to revisit

- When the owner picks a third-party agent: run it through the released proxy on the repair task (G1's bar).
- When a notes reply is refused for size in a run that matters, or a task runs long enough to hit it repeatedly:
  look at the cap before changing anything else.
- A 1.0.1 only for a bug a user reports or a lab run finds; quality changes go through a registered campaign and a
  new release gate.
