# Follow-up after the 640×384 W2 screen

Design only, based on sealed packet 102; no endpoint, GPU request or runtime edit
was made. Execution remains conditional on 102 actually passing. Keep a successful
application alive while preparing the next experiment, as the owner's current
instructions require. Preserved 101c/102 evidence covers three fixtures, not the
full original suite or endurance.

## The current application cannot admit an extension

`session.configure` and `integration.install` are one-shot. The authority binds a
single plan hash, rejects unknown/reused request names and prompt IDs, and permits
only forward phase transitions. Its native-reference gate requires zero sampler
routes, lean state and decoder replicas. Those optimized states are present after
qualification; the native adapter has also closed. The integration actions are
finite, one-shot and use fixed output paths. A new client manifest cannot change
any of this. Sending an invented prompt risks latching the session as failed.

Therefore **a controlled application reload with a sealed successor is needed**
for the ten-fixture extension. Rebinding the authority, editing loaded source,
clearing its completed list, unfreezing captures, or pretending new clips are
native references would invalidate the evidence. This is an application reload,
not a host reboot, driver action, or restart chain. Preserve the entire successful
102 identity and receipts before the reload; no immediate stop is needed merely
because its finite screen finished.

## Smallest useful successor

Use all ten original fixtures in their original order: boat, marble, bird,
pendulum, rain, paper, candle, pour, fabric, wheel. All already declare encoder
window 64 in `data/stability-01-window-prereg.json`; preserve their prompts and
seeds. Keep 640×384, 25 frames, BF16, 8+3 steps, 23/25 split, shared graph pool,
batch one and the accepted encoder arithmetic.

Before installing optimized state, create **20 native captures**, two serial
passes over the ten fixtures. Require each repeat pair to match all four tensors,
with actual residency/precision observations and the existing no-fallback guard.
The repeated first three fixtures also bridge the expanded oracle to 101c/102;
compare their bytes without borrowing old server identity claims. Then qualify
both workers and decoder replicas, followed by 14 candidate requests emitting ten
clips and 14 timed requests emitting ten clips. Four fills in each phase are
excluded. Every emitted clip must match its same-size native oracle. Timed claims
remain a short ten-fixture screen until longer stability and repeated timing exist.

This needs 50 raw captures including two capture-setup requests. At 74,620,672
payload bytes per full capture, that is about **3.475 GiB**, before headers,
previews and logs. A fresh **4-GiB write allowance plus the 50-GiB free reserve**
is a plausible admission budget, not permission to exceed it. Check actual file
sizes and available space before sealing; raise neither budget silently. Update
the server, client, plan and setup schedule together from the old 32-capture cap
to exactly 50, with bounded total attempts and no retries. Keep original references
and failure evidence. Do not assume unused capacity from 102 carries over.

## Make later reuse explicit before this reload

The successor should include a narrowly scoped continuation mechanism from the
start, so future same-shape endurance blocks can reuse its loaded application.
Prefer a finite list of reviewed extension-manifest hashes over arbitrary JSON
plans or executable plug-ins. Each block binds its predecessor completion receipt,
source/runtime/server identity, oracle-set hash, exact ordered graphs, unique names
and indices, maximum attempts/captures, deadline and fresh disk allowance. It may
only add optimized requests with unchanged already-qualified numerical identity;
it cannot create native references or change geometry, precision or worker policy.

Admit a block once, under the existing authority/action lock, only after exact
verification of its predecessor and actual queue, pipeline and preview quiescence.
Record completed tails before releasing them. Recheck physical free memory,
resident owners, frozen captures, and absence of faults; retain the native OOM
refusal. Write a durable admission receipt before the first request. Never reset
prior failures, consumed identities, prior disk accounting or verification state.
Account each new allowance separately and keep an aggregate ledger; newly freed
bytes must not hide writes. Faults halt new requests; success leaves the application
available. The first practical extension can be a bounded 30-emission endurance
block cycling all ten fixtures, with its own 34-capture limit and roughly 3-GiB
allowance; it is stability evidence, not a new throughput record.

This requires changes to session authority, integration, client admission and
verifiers, plus negative controls for replay, mismatched identity, stale evidence,
busy admission and over-budget requests. If that is too much for the next measured
step, preregister the finite full-suite and endurance phases in one successor plan
instead. Avoid building a general job service to solve this one need.

## Keep the W1 comparison honest

101c and 102 can compare the same three-fixture serial-client screen, provided
actual client/source/timing identities are diffed. Their different fill depths are
excluded consistently. They cannot establish a ten-fixture W1-versus-W2 result.
Do not switch to queued submissions only for W2 and attribute all improvement to
workers; delivery changes need their own matched control.

A future same-process comparator could pin dispatch to one already-qualified
worker, then release dispatch to both at a quiescent phase barrier. Current source
ignores the pin after freeze and only permits worker-count increases, so this is
**not currently admitted**. A successor would need explicit reviewed per-phase
dispatch and truthful receipts. Label it “one active sampler worker with two
resident graph sets,” not the original W1 configuration. Independently gate the
outputs of each dispatch mode; retain the same serial client and fixture order.
Twenty native references, 13+14 candidate requests, 13+14 timed requests and two
setup captures would total 76 raw captures, about 5.282 GiB of tensor payload;
a roughly 6-GiB allowance would need actual disk admission. This paired experiment
has clearer attribution but more code and storage cost than first qualifying W2
across all ten fixtures. The recommended order is full-suite W2, bounded endurance,
then this matched dispatch control if 102 shows a material speed improvement.
