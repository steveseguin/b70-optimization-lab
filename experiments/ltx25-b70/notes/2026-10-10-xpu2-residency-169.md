# Packet 130: xpu:2 inventory and the 169-frame admission shortfall

The saved receipts identify **2.400–3.856 GiB of reserved but unallocated
memory on xpu:2** near the refused request. Releasing eligible allocator cache
before the display admission check is the smallest change worth qualifying.
It changes allocation ownership, not model arithmetic. **These counters do
not prove how much the allocator can release. No native release was performed.**
The guaranteed released amount from this CPU investigation is zero; the saved
evidence supports a candidate, not a declaration that 169 frames now fit.

The exact base shortfall is **0.615982 GiB**, close to the brief's rounded
0.63 GiB. A further 0.5 GiB avoids the near-floor band. There is also an
existing **0.75 GiB screening allowance** in the actual replica admission
code, omitted from its error wording. Preserving that allowance requires
**1.365982 GiB**, not merely 0.8 GiB, more free memory at the refused sample.
The 6.5 GiB transient reserve, 2 GiB physical floor, and 0.75 GiB screening
allowance must all stay unchanged.

The native `torch.xpu.empty_cache()` API has no device argument and calls
`torch._C._xpu_emptyCache()`. An xpu:2 device context is not proof that only
that card's cache is touched. The implementation must describe that scope
truthfully, leave live weights/graph storage and peak counters intact, and
record before/after physical-free and allocator counts. Returning an eligible
block to the device allocator is distinct from dropping the host page cache
or changing a host memory setting. No cache release was executed here.

## Recommendation and what remains open

The launch option is `LTX_DISPLAY_ALLOCATOR_RELEASE=before-admission`, with
default `off` preserving parent 129. It makes one bounded cache release only
when the current budget cannot pass, then takes a fresh reading; it does not
release cache unnecessarily on already-admissible calls. Four-card counters
before and after are observed net deltas during concurrent work, not isolated
measurements of the release's effect.

Use this allocator remedy on parent 129, scoped to the intended
169/frame/cone/dg0/eager-display/parallel/xpu:2/legacy arm. Admit only after a
fresh physical-free check passes the unchanged 9.25 GiB pre-decode requirement;
repeat the check for every decode and preserve the post-decode and observed
growth guards. A failed release is a refused experiment, never a retry loop or
automatic placement fallback. An exact-copy test, all nine full-image
qualification comparisons, three-chain identity, per-chunk cone/display bytes,
fault checks, and sustained plateau measurements still belong to the coordinator.

Use **6.20–6.65 seconds per seven seconds of new video (0.886–0.950 s/s)**
as the inherited conditional scheduling forecast, center 6.30/0.900. Cache
release adds unmeasured synchronization/reallocation cost; contention could
instead yield the inherited 6.65–7.20 seconds (0.950–1.029 s/s), or worse if
release becomes expensive. No measured 169 cadence exists for this candidate.
It must beat **6.378 seconds** to beat the current 145 record of 5.467/6 s/s.

Open: actual released GiB, exact pool/cache sub-inventory, allocator scope at
runtime, latest169 concurrency peaks, complete native qualification, stable
per-card margins, and repeated speed. CPU tests cannot close any of these.
