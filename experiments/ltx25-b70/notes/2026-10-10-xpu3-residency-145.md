# Packet 131: xpu:3 memory for the 145-frame cone graph

Moving display to the exact xpu:2 replica is the useful first remedy, but
**moving it alone does not prove that the graph fits**. The native full-image
references remain on xpu:3 during qualification. Their reserved allocation tail
can survive into the next cone. The existing cone graph already captures only
`forward_pre_diffusion` into its own decoder pool; selecting that method or
calling the pool private does not itself save another byte.

The CPU [analysis script](../data/resume-20261008/continuation131-memory-analysis.py)
and [frozen census](../data/resume-20261008/continuation131-memory-analysis.json)
read 1,059 hashed input files. They include all qualification rows and stream
rows through sequence 200 for packets 124, 127, two 128 configurations and 129.
For the still-growing 129 run, this is a fixed window: 210 receipt/decode pairs,
including nine qualification pairs. No GPU imports, probes, live requests or
writes into existing runs were used. No scratch directory was created.
All numbers below are GiB (2^30 bytes) unless marked otherwise.

## Cone-only graph memory need

Both121-frame packet119 and120 `stream-freeze.json` records contain exactly
one capture: `forward_pre_diffusion`. Input shape is1×128×16×8×8;
output is1×121×64×64×256 BF16. `forward_diff_step` has zero signatures,
zero captures and zero replays: the cone wrapper uses its own restricted
stage5 path. Packet120 records:

- Before capture: allocated15,466,932,736 B; reserved17,217,617,920 B.
- After capture: allocated16,518,136,832 B; reserved20,648,558,592 B.
- Exact observed reserved growth: **3,430,940,672 B =3.1953125 GiB**.
- Exact observed allocated growth: **1,051,204,096 B =0.979010105 GiB**.

The counter is sampled inside `_capture`, before its proof-local tensors go
out of scope. It includes warm-up/proof allocation and pool reservation, not
only permanent graph storage, and it is not an isolated capture peak.

At145, latent time grows16→19. Applying the requested temporal² rule gives
**3,430,940,672 ×(19/16)² =4,838,162,432 B =4.505889893 GiB**
(4.838162432 decimal GB). The linear scenario is4,074,242,048 B
=3.794433594 GiB. These are engineering estimates. **An exact145 memory
requirement or proven upper bound cannot be measured by this CPU-only task.**

On129's worst saved phase, subtracting the quadratic growth leaves
**10.806747−9−4.505890 =−2.699142 GiB**. Using127's lower minimum gives
−2.831944 GiB. The clean cone boundary is more generous, but cannot erase
that retained allocation at other phases.

The implemented `LTX_CONE_GRAPH_MEMORY=replica-release` option requires a
conservative5GiB capture reserve plus9GiB floor and0.75 screening: **14.75GiB
before the first capture**. Later cone admissions require **9.75GiB**, because
the captured graph is already resident. Each admission performs at most one
process-wide unused-allocator-cache release, and only if its initial physical
reading fails; a fresh reading must then pass or the graph experiment latches.
The candidate checks that only `forward_pre_diffusion` is captured, refuses
measured capture reservation growth above5GiB, and requires at least9.75GiB
free immediately after capture. These checks do not make5GiB a hard allocation
limit. Default `off` retains parent130 execution.

The saved124 stream cone minimum14.552792 would miss the14.75GiB
first-capture requirement by0.197208 without actual release. Passing a fresh
admission after release is necessary, not proof that every later reference,
audio and text phase will remain safe. Physical sample minima, plateau,
qualification bytes and repeated speed remain for the coordinator.

The speed target transfers the121 measured cone gain of about0.19s onto
