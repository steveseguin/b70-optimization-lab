The own runtime, in plain terms

A custom inference engine the lab built for Qwen3.8 Flash-Next on Arc Pro B70 cards. It exists to prove two things at once: speed (sealed records) and exactness (every published output byte-identical to its oracle, with receipts). This page is the honest version: what is measured, what is capped, and what the engine refuses to claim.

The short version

  • It is a research engine, not a product. There is nothing to download and install today; the reproducible artifacts are the lab's recipes and evidence, linked below.
  • It is fast where measured: 58.557–58.632 tok/s decode on two B70s and 31.510–31.782 tok/s on one, with prompt reading at 75.884–75.973 and 32.595–32.752 tok/s respectively — every figure from sealed, receipted runs.
  • Exactness is a gate, not a hope. A run that cannot prove itself byte-identical does not publish.
  • Checkpoint/restore works, and is still labeled experimental: on 2026-10-22 a one-card session was saved at 256 tokens, restored in a fresh process and continued; the merged output matched an uninterrupted run byte for byte, twice. Restore took 0.46 s where re-reading the prompt took 36.75 s. Later the same day a second engine revision passed the harder test: restore a saved session, add a new 126-token turn, and the answer matched a fresh one-shot run byte for byte; saving again after a restore and resuming from that second save matched too.
  • The gaps are declared, not hidden: 128-token oracle caps, a two-card rebuilt-binary qualification still pending (the one-card rebuild passed on 2026-10-22), no sampler, no multi-user controller, no context curve beyond 4,096 tokens.

What the engine is

The own runtime (own-xpu-runtime) is a custom SYCL/Xe inference engine for Qwen3.8 hybrid-architecture models on Intel Arc Pro B70 GPUs, built and validated in this lab under a fail-closed packet campaign. Qwen3.8 Flash-Next is a hybrid: 48 layers made of 36 GDN (gated delta net, linear attention) layers and 12 QSA full-attention layers, a 512-expert top-10 mixture-of-experts, and a PLE early layer. The engine is designed around that exact structure — per-layer plans, a resident expert cache, snapshot banks — instead of inheriting generic kernels from a general-purpose runtime.

Why build one at all, when vLLM and llama.cpp already serve this hardware? Two reasons, and neither is a claim of exclusivity: those runtimes remain excellent and are the right choice for most setups on this site. The lab wanted (a) an architecture-fit kernel plan for this specific hybrid, and (b) engine-level access to session state — checkpoint/restore, residency, future context features — that frontends do not expose. Owning the whole stack makes both possible.

Pending, on purpose

Strict quality promotion for the full512 profiles is pending and labeled as such on the packages. Oracle coverage beyond 128 tokens is an explicit, declared gap. The portable source rebuild (42 translation units) produces a binary with a different hash than the sealed historical one, so it needed its own device qualification: the one-card rebuild passed on 2026-10-22 (31.83 / 31.81 tok/s, outputs identical to the sealed line; window record). The two-card rebuild has not been run on device yet, so the two-card package's published numbers still belong to the sealed historical binary — and the package says so.

Exactness is the gate

The campaign's discipline: sealed sources, admission-checked device windows, fresh-process determinism, oracle prefixes, and fail-closed comparisons. An output that cannot be shown byte-identical to its oracle — or to an independent repeat run — does not get published as a result. That is why the table can carry a requalification at all: on 2026-10-20 the sealed full512 profiles were re-measured fresh — 58.724 / 58.676 tok/s two-card and 31.766 / 31.774 one-card — with outputs identical to the original sealed qualification. On 2026-10-22 the same gate was applied to two new binaries on one card: the portable rebuild (packet178) and the checkpoint engine (packet179, a relink of the sealed sources). Both produced all 12 suite outputs identical to each other and to the sealed line, at 31.83 / 31.81 and 31.85 tok/s.

Session checkpoint/restore Experimental

One capability the custom stack unlocks is whole-session checkpoint/restore: save a computed session, stop the engine, restart, restore, and keep decoding. The contract — save/inspect/restore/delete, compatibility checks, prefix-plus-delta rules, and the exactness gates — is written down in the session-swap design (v1.2).

What passed on 2026-10-22 (one card, same-generation resume): a request ran to token 256 and was saved (1.10 s, 68.8 MB in 128 state blobs). Two separate fresh processes each restored it and decoded 128 more tokens. Both merged 384-token outputs equal the uninterrupted reference run at [0:384), the two restores are identical to each other, and the first 128 tokens match the oracle. Restore took 0.46 s; re-reading the same 256-token prefix from cold took 36.75 s. That is the design's gates 1–4 (restart-and-continue, repeat determinism, cold-start comparison, admission discipline). Receipts: packet179 checkpoint row.

What passed later on 2026-10-22 (packet180, one card): the second engine revision adds the operations the integration review asked for: append a new turn to a restored session, restore then save again under a new id, one manifest source of truth (a tampered side file is refused before any device upload), one shared lock for save/restore/delete, and inspect in a single-JSON or metadata-only form. On device: a session saved at 256 tokens was restored in a fresh process, given a new 126-token turn, and its 128-token answer equals a fresh one-shot run of the whole input; the re-saved session resumed for 64 more tokens and matched too; a repeat produced identical tokens and a byte-identical saved state. Restore took 0.41–0.46 s and the appended turn's prefill 5.59 s, against 16.0 s to read all 469 tokens from cold. Receipts: packet180 lifecycle row.

Why it is still labeled experimental: the checkpoint manifest keeps the string label: "experimental" until an engine revision changes it (the next relink), and ctxkeeper does not call these operations yet. The appended turn's 5.59 s is the cost of a fresh process with an empty expert cache (the reference run's first 126 positions took 5.68 s); in a long-running server the same append runs at the warm rate.

Honest non-goals today

  • No sampler. Greedy argmax only — there is no RNG state, temperature, or top-k/p anywhere in the engine.
  • No multi-user controller. The packet165 controller is sequential; concurrency curves exist only for the vLLM FP8 packages on this site.
  • No context curve for the own-runtime full512 profiles. Measured at 4,096 tokens; other capacities are unmeasured, not claimed.
  • No ctxkeeper adapter yet. Append and re-save are qualified on device, but nothing outside the lab harness calls them, and the saved-state label is still experimental.
  • No shipped product. The runtime is a lab engine under active qualification. What you can take away today are the recipes and evidence below — not a download.
