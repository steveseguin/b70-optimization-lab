Hardware setup

Host stability

Our four-card B70 machine froze again and again for three weeks. It looked like one problem. It was four, and the biggest one was plain faulty memory that nothing on the machine could report. This guide shows what each fault looked like, how many times it happened, and the checks that told them apart, so you can run the same checks on your own box.

The short version

  • 34 of 38 boots ended badly between September 13 and October 3, 2026. Lab-measured
  • The main memory was faulty, and it has no error correction, so no error was ever logged. A memory test over 104 GB failed in 13 minutes. An earlier test over 64 GB had passed.
  • A targeted test found the bad spots: eleven small regions, about 45,000 wrong values per minute. The machine reset itself during that test with every GPU idle.
  • We switched the bad memory off in software (10 GB of 125), tested the rest twice, and got zero errors.
  • Separately: one GPU sometimes stops answering, a CPU idle-state bug caused idle freezes, and a debugging setting turned stalls the machine survived into silent halts.
  • One popular theory, "the disk dies first", was wrong. It was the system log's five-minute save interval.

Silence is not health

Across all of this the machine logged zero hardware errors. On a board without error-correcting memory there is nothing to report a memory fault, and on this board the firmware keeps PCIe errors to itself. "No errors logged" told us nothing.

Fault 1: bad memory with no error correction

The board holds four ordinary 32 GB memory modules without error correction (ECC). That is a property of the modules, not a setting. It is a different thing from the B70's own VRAM ECC, which you can switch on and off.

Check what you have

sudo dmidecode -t 16 | grep 'Error Correction'    # None = no ECC
ls /sys/devices/system/edac/mc                    # empty = nothing can report memory errors

Test nearly all of it

sudo apt-get install memtester
for i in 1 2 3 4 5 6 7 8; do sudo memtester 13G 1 > worker-$i.log 2>&1 & done

Size the workers to cover everything except 15 to 20 GB. Run it with the GPUs idle. Coverage mattered: our fault sits in the top quarter of memory, and a smaller test never touched it.

Every error was in the same byte of each 8-byte value, and the bad byte held the previous value: a write that did not land. One byte position only points to one memory chip on one module. It was intermittent, which is why short tests passed.

Switch off the bad part without rebooting

Linux can take blocks of memory out of use while running. Our tool logs each error by physical address; divide the address by the block size to get the block number.

sudo python3 tools/physmap_memtest.py --gib 104 --tail-mib 8 --rounds 12 --out run.jsonl
cat /sys/devices/system/memory/block_size_bytes          # ours: 2 GB blocks
for n in 53 54 55 56 57; do echo offline | sudo tee /sys/devices/system/memory/memory$n/state; done
sudo python3 tools/physmap_memtest.py --gib 99 --rounds 2 --all --out after.jsonl
This is a workaround

The blocks come back after every reboot, so the command has to be run again each time. The real fix is replacing the module. Until bad memory is switched off or replaced, do not install system updates and do not trust any measurement from the machine.

Fault 2: one GPU stops answering

Three times the kernel reported a processor stuck inside the Intel GPU driver, reading a message from a card that did not reply. It was the same processor each time, and that processor handles one specific card. The machine recovered from the first two after 16 and 72 seconds. We do not yet know whether the card, its slot, its power cable or the driver is at fault. Swapping the card to another slot is the test.

journalctl -k -b -1 | grep -A12 'hard LOCKUP'            # look for xe_guc_irq_handler
i=$(ls /sys/bus/pci/devices/0000:43:00.0/msi_irqs | head -1)
cat /proc/irq/$i/effective_affinity_list                 # which CPU serves this card

Fault 3: the CPU's deep idle state

Two boots died with one processor waiting forever for another, one of them minutes after startup with nothing running. This is a known problem with deep idle on some AMD processors. Turning off the deepest idle state ended it: the next idle boot ran 5.6 days. The BIOS setting Power Supply Idle Control = Typical Current Idle is the cleaner fix.

Fault 4: a setting that hid the evidence

We had told the kernel to stop on any lockup so we could read the trace. Nothing was set up to save that trace, so the machine just stopped. A stall it had survived twice became a permanent silent freeze. Only use panic-on-lockup when something will catch the panic.

The false lead: "the disk dies first"

The system log stopped up to five minutes before each freeze while work carried on, and files written just before the freeze came back empty. Both are normal. The log is saved to disk every five minutes, and file data about 30 seconds late. A freeze loses whatever was not yet saved. The disk was healthy. To keep a machine's last words, send kernel messages to another computer, or follow the kernel log into a file and sync after every line.

What we have not shown
