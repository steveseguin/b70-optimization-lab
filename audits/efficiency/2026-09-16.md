## Verdict

The lab is genuinely fast this week where it matters: two exact, multi-server-verified
speedups landed (LTX graph capture, Qwen3.8 27B one-card FP8), each following real
determinism debugging rather than guesswork. But the measuring stick this session
started from was broken — the checkout was a shallow git clone, which made the
audit's own metrics script report 421 "campaigns this week" with fabricated 0-hour

729 commits and only 4 campaigns detected by the script's glob — itself an
undercount (see below). Net: throughput this week cannot be judged from the tool's
own numbers without the fix proposed here; qualitatively, wall-clock went mostly to
repeated GPU faults and negative screens, not to the two eventual wins.

## Top three changes

1. **Unshallow (or verify depth of) the clone before every scheduled audit.**
   Evidence: this session's clone was shallow; `campaigns_total` was 421 with
   0h/0h latency, entirely from files misattributed to the 2026-09-14 23:26:14
   boundary commit, versus 4 campaigns / n=0 after `git fetch --unshallow`.
   Expected saving: prevents every future weekly report from publishing fabricated
   throughput and latency numbers. Generalizes to any lane, any week, any fresh
   checkout.
2. **Widen `efficiency-audit-metrics.py`'s campaign glob** from
   `experiments/*/data/*prereg*.json` to also match nested
   `experiments/*/data/*/preregistration.json`. Evidence: `git log --diff-filter=A`
   in-window shows 7+ more preregistrations under that nested layout (e.g.
   `experiments/ltx25-b70/data/metadata-dispatch-cpu-01/preregistration.json`)
   the current glob misses. Expected saving: restores visibility into lanes using
   the nested convention, avoiding understated throughput. Generalizes to every
   lane adopting that layout (already ltx25-b70 and newer qwen38-27b-b70
   campaigns).
3. **Pre-authorize the bounded XPU/XCCL health probe as the runner's automatic
   first post-fault step**, not a live-approval gate. Evidence: CURRENT.md's
   09-16 06:05 entry calls the probe "the normal first check once approved" —
   three faults this week (09-14 18:30, 09-15 02:20, 09-16 06:02) each stopped
   work for a human round trip before that routine check could run. Expected
   saving: shrinks fault-to-resume wall-clock on future faults on either host,
   while still escalating the reset/reboot decision itself to the user.
   Generalizes to any lane on either host after any future GPU fault.
